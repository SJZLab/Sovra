# FTF-UX00 — Heuristic audit, 2026-10

**Status:** PROVISIONAL / L1-PROVEN. Docs only — no production code touched. Per
`docs/design/UX_STANDARD.md` §4.5, this producer's own evaluation is one evaluator; NN/g
recommends several, so an independent second evaluation of a sample (Control plane, L2) is
required before this entry can be treated as the certified baseline for the UX02–UX07 slices.

**Scope:** every component under `apps/web/components/` as it exists on `main` today (16
files, listed below), evaluated against NN/g's 10 usability heuristics across the states each
component actually has. No component is wired to a live page yet (FTF-H029 has not landed —
Law 6/7, disclosed, not a finding of this audit); `apps/web/styles/tokens.css` and the shared
`apps/web/components/ui/` library named by FTF-UX01 do not exist yet, so every component today
renders plain, unstyled native HTML elements. Findings that depend on the token/shared-component
foundation are marked "blocked on FTF-UX01" below rather than double-counted per component.

**Method:** read every component's full source (production code, not its test file) directly;
cross-checked against `docs/design/UX_STANDARD.md` §3 and against the vendored skill. No design
system was generated (`--design-system` is not used — §72.1 fixes the token values; CLAUDE.md
"UI design standard"). Skill queries run (`--domain ux`, `.claude/skills/ui-ux-pro-max/scripts/
search.py`), each with the guideline(s) applied below:

| Query | Guideline(s) applied |
|---|---|
| `form validation` | Submit Feedback (High); Form Labels (High) |
| `error message` | Error Messages — must be announced, `role=alert`/`aria-live` (High); Error Placement — inline, `aria-describedby` (High) |
| `confirmation dialog` | Confirmation Dialogs — confirm before delete/irreversible actions (High) |
| `loading state` | Loading Indicators — match expected wait, `aria-busy` (High) |
| `empty state` | Empty States — helpful message + action (Medium) |
| `destructive action` | Confirmation Dialogs (High, same as above) |
| `progress indicator` | Progress Indicators — step/percentage for multi-step processes (Medium); Focus States — visible focus ring (High, noted as blocked-on-tokens below) |

`data table`, `loading state` (react stack), `long running job progress` and `confirmation
dialog` (react stack) returned 0 matches on `--stack react` and are recorded as such, per the
skill's own rule (no invented guideline); the `--domain ux` (platform-agnostic) queries above did
match and are what is applied.

## Per-component findings

### 1. `identity-and-tenancy/oidc_login.tsx` (FTF-0101) — UX07
States: populated only (a static link; no loading/error/empty state exists in this component —
the redirect and any provider-side failure happen off-component, after navigation).
- **H10** (minor, sev 1): no text near the link names which identity provider the user is about
  to be sent to, or what to expect next. Guideline: Loading Indicators'
  sibling principle ("avoid... leaving long waits unexplained") applies by extension to the
  pre-navigation state. §72 clause: none (pre-shell). Fixed by: UX07.
- Everything else about this component is correctly minimal for its own stated scope (a real
  top-level `<a>`, never a JS redirect — H5/Law 17 met).

### 2. `artifact-capabilities/capability_compatibility_ui.tsx` (FTF-0309) — UX05
States: empty (not yet loaded), loading, populated, error.
- **H1** (minor, sev 1): "Check compatibility" relabels to "Checking…" with no `aria-busy`
  (cross-cutting X7).
- Strength: `trainBlockers` surfaces every real reason Train is disabled in one list (H1/H9 met
  well — this is the strongest "visibility of system status" implementation in the set).

### 3. `artifact-capabilities/model_to_artifact_mapping_ui.tsx` (FTF-0308) — UX05
States: empty, loading, populated, error, confirm (alertdialog).
- **H1/H7** (minor, sev 2): the mapping, the artifact picker and the change history are three
  independently-triggered loads ("Load mapping" / "Load artifacts" / "Load change history") with
  no auto-load on mount and no indication that three separate actions are needed to see the full
  picture. Guideline: Submit Feedback / general visibility. §72 clause: §72.1. Fixed by: UX05.
- Strength: the confirm step (`role="alertdialog"`) names the exact consequence ("invalidates
  related qualification... evidence recorded against catalog version N will no longer apply") —
  this is the right pattern per "Confirmation Dialogs" and should become the shared `Dialog`
  component other slices copy.

### 4. `cost-and-model-search/costprofile_schema_ui.tsx` (FTF-1301) — UX05
States: loading, populated (with per-row certified/disqualified), error.
- **H5** (minor, sev 1–2): `currency` is a free-text `<input>` (uppercased client-side) rather
  than a closed list of ISO-4217 codes — a typo produces a real, persisted bad currency. §72
  clause: §72.1 (form rules — constrain input before submit). Fixed by: UX05.
- Strength: "Display unknowns honestly" is executed exactly as the acceptance clause names it —
  every disqualified reason is shown with its own reason, and the cheapest-certified panel has a
  real, worded empty state ("No certified cheapest rate yet -- record and verify a rate to see
  one here.") that already matches the Empty States guideline ("helpful message and action").

### 5. `dataset-factory/dataset_issue_resolution_ui.tsx` (FTF-0516) — UX02
States: empty, loading, populated, error, decision-form (with its own sub-states).
- **H2** (minor, sev 2): the per-issue action button is labelled `Review {issue_id.slice(0,8)}`
  — a truncated UUID fragment, not a word a reviewer would use to recognize which issue it is.
  Guideline: Form Labels / general "match with the real world". Fixed by: UX02.
- **H1/H8** (minor, sev 2): blocking vs. warning severity is text-only (`"${entry.severity}
  ${entry.detector}/${entry.category}..."`) with no visual distinction (icon/colour) between the
  two — blocked on tokens (§72.2 StatusBadge). Fixed by: UX01 + UX02.
- Strength: the before/after evidence digests, rationale requirement (1–2000 chars, trimmed,
  never blank) and the `problems` pre-submit checklist are a genuinely strong H5/H9
  implementation — better than most of the set.

### 6. `dataset-factory/dataset_source_selector_purpose_authorization_ui.tsx` (FTF-0500A) — UX02
States: empty list, populated list, form, preview, authorize (idle/checking/authorized/denied).
- **H10** (minor, sev 1): the credential `<input type="password">` has no helper text about what
  is/is not stored or re-displayed (the component itself never re-displays it, correctly — this
  is purely a missing reassurance to the user at the point of entry). Fixed by: UX02.
- **Empty state** (minor, sev 2): the connection list renders nothing (`<ul>` with zero `<li>`s)
  when there are no connections yet, with no "no connections yet — create one" message.
  Guideline: Empty States. Fixed by: UX02.
- Strength: the preview step explicitly disambiguates itself from a real source-metadata preview
  ("it is not a preview of the external source's own records... no connector in this repository
  can validate yet") — this is the right way to disclose a scope boundary to the user rather than
  silently doing less than the name implies.

### 7. `dataset-factory/resumable_dataset_upload_ui.tsx` (FTF-0501-UI) — UX02
States: idle, resumable, creating, uploading, interrupted, ready_to_finalize/incomplete/conflict/
finalize_retry/storage_unavailable, finalizing, accepted, already_verified, malformed, expired,
rejected.
- **H5** (**major, sev 3**): "Abandon this draft and start a new upload" discards an in-progress,
  possibly-large multipart upload session with a single click and no confirmation step.
  Guideline: Confirmation Dialogs — "Confirm before... irreversible actions... Don't: Delete
  without confirmation." §72 clause: §72.2 (destructive-action discipline the rest of the file
  already applies to the dataset-source/mapping/issue components). Fixed by: UX02.
- **H3** (minor, sev 2): there is no explicit "Cancel" control during the active `uploading`
  phase itself (only after an interruption can the user resume or abandon) — guideline: Progress
  Indicators' sibling user-control principle. Fixed by: UX02.
- **H1** (minor, sev 1): progress is a raw count ("Uploaded X of Y parts"), never a percentage or
  bar. Guideline: Progress Indicators. Fixed by: UX02.
- Strengths: this is the most rigorous component in the set for Law 17/negative-acceptance —
  every one of the typed failure codes is mapped to a specific, correct UI consequence
  (closed/expired/incomplete/conflict/storage_unavailable/refused/retryable), and the
  resume-after-reload flow (re-hash the re-picked file before trusting the draft) is exactly
  right.

### 8. `evaluation-factory/evaluation_case_editor_import.tsx` (FTF-0602) — UX06
States: empty, populated, restricted, import (idle/error), edit (idle/error).
- **H5** (minor, sev 2): `input_json`/`expected_json`/`grader_config_json` are free-text JSON in
  plain `<textarea>`s with no schema hint or live validation — only validated on submit.
  Guideline: Form Labels' sibling input-constraint principle. Fixed by: UX06.
- **H9** (minor, sev 2): import field errors are reported as a flat `Row N / field: code` list
  with no visual correlation back to the pasted/uploaded rows (the user must count rows by hand
  in their own file). Guideline: Error Placement. Fixed by: UX06.
- Strength: the independent-critical-grader check (blocking a model-self-report critical case in
  the browser *and* independently on the server) and the "no case content is shown" 403 handling
  for restricted final suites are both real, correctly-enforced negative-acceptance behaviour,
  not merely a client-side illusion.

### 9. `litellm-gateway/model_catalog_ui.tsx` (FTF-0214) — UX05
States: projects (empty/populated/error), catalog (unloaded/populated/error), probe (idle/running/
result/error).
- **H5** (**major, sev 3**): "Run probe" triggers a real, paid, external-provider call
  (chat/streaming/tool_call/structured_output) with no cost estimate or confirmation step before
  it fires — only an organization-admin role gate decides *who* may click it, not whether the
  click itself is informed. Guideline: Confirmation Dialogs — "confirm before... irreversible
  actions" (a paid external call is not undoable). §72 clause: §72.3 (dense ops console — a cost
  figure belongs in the same row). Fixed by: UX05.
- **H7** (minor, sev 1): status/metadata filters require a second manual "Load catalog" click
  rather than refetching on change. Fixed by: UX05.
- Strength: `selectedProjectId` genuinely starts `null` and gates both Load-catalog and Probe —
  the "explicit project selection" and "viewer cannot run paid probe" negative-acceptance clauses
  are both met for real, not just visually.

### 10. `project-mandate/project_schema_api_ui.tsx` (FTF-0401) — UX04
States: create, edit, saving, draft-saved, error.
- **H8** (minor, sev 1): "Save changes"/"Create project" and "Save draft" are two
  equally-weighted buttons side by side with no primary/secondary visual distinction (blocked on
  tokens — §72.1 Button variants). Fixed by: UX01 + UX04.
- Strength: `project_type` is correctly disabled once editing (matches the backend's own
  immutability rule) and `agent_objective` only renders when relevant — good progressive
  disclosure (H8) already.

### 11. `project-mandate/requirements_ui.tsx` (FTF-0408) — UX04
States: loading, populated, conflict rows, budget form (create/edit), error.
- **H5** (minor, sev 2): the budget form does not compute or warn if a typed `total_amount`
  would be less than the already-`reserved_amount` shown two fields away — the user can submit a
  value the backend will presumably reject, with no pre-submit hint. Fixed by: UX04.
- Strength: the desired/observed/enforced conflict row (`requirement-conflict-*`) is exactly the
  "show observed/desired/enforced conflicts" negative-acceptance clause, computed fresh on every
  render from live data, never a stored/overridable flag — correct by construction.

### 12. `target-application/candidate_selection_ui_no_auto_selection.tsx` (FTF-04A18) — UX03
States: empty, populated, selecting, confirmed, error.
- **H2** (minor, sev 1): `confidence_score` is shown as a bare number with no unit/scale
  (0–1? percentage?). Fixed by: UX03.
- Strength: this is the cleanest "no auto-selection" implementation in the set — `confirmed`
  starts `null`, is set only from a real POST response, and the list is never re-sorted by score.

### 13. `target-application/github_accessible_repository_selector_ui.tsx` (FTF-04A03) — UX03
States: credential form, loading, populated, empty-after-search, error.
- **Empty state** (minor, sev 2): zero repositories returned after a real search renders nothing
  — no "no accessible repositories found for this credential" message. Fixed by: UX03.
- **H10** (minor, sev 1): the token `<input type="password">` has no guidance on required scope
  or where to obtain one. Fixed by: UX03.
- Strength: pagination (`has_next_page`) is real and selection genuinely starts `null`.

### 14. `target-application/github_branch_ref_selector_immutable_sha_resolver.tsx` (FTF-04A04) — UX03
States: branch list (loading/populated/error), ref form, resolved, error.
- **H7** (minor, sev 1): the ref `<input>` has no default/pre-fill (e.g. the connection's own
  `default_branch`), so every use requires a manual pick or type even for the common case. Fixed
  by: UX03.
- Strength: `handleRefChange`/`handleSelectBranch` both clear any previously resolved SHA
  immediately — "does not mix commits" is enforced in the UI layer, not only trusted to the
  backend.

### 15. `target-application/mandate_editor_and_conflict_resolution_ui.tsx` (FTF-04A22) — UX03
States: loading, editable, read-only (locked/review_required-false path), conflict list,
add-forbidden-action, save (idle/error), refresh (idle/error).
- **H10** (**major, sev 2**): eleven structured mandate fields (`business_purpose`,
  `tool_side_effect_confirmation_policy`, `escalation_abstention_behavior`,
  `privacy_security_profile`, etc.) have zero inline guidance on what belongs in each —
  these are genuinely non-obvious domain concepts (Section 7A.6), not self-explanatory labels.
  Fixed by: UX03.
- **H5** (minor, sev 2): the six list fields (`allowed_responsibilities`, `required_tools`, …)
  are edited as a single comma-separated `<input>` — a stray comma or trailing space silently
  changes the list on parse; no chip/tag editor. Fixed by: UX03.
- Strength: `evaluateForbiddenAction`/`mandateLockBlockers` are pure functions of live
  desired/observed/enforced data with no override/acknowledge control anywhere in the component
  — the negative-acceptance clause ("user override cannot declare a dangerous runtime safe") is
  structurally unbreakable here, not merely discouraged by copy.

### 16. `target-application/manifest_review_edit_ui_with_per_field_evidence.tsx` (FTF-04A21) — UX03
States: loading, populated (14 fields × clean/unsaved/invalid/conflict), evidence, lock-blocked,
error.
- **H8** (minor, sev 2): all 14 JSON fields render unconditionally and in full (no progressive
  disclosure/collapse), making this the longest, most cluttered screen in the set. Fixed by:
  UX03.
- **H5** (minor, sev 2): JSON fields are raw `<textarea>`s with no schema hint, same class as
  finding 8 above. Fixed by: UX03.
- Strength: the conflict mechanism (stored draft's own `baseText` vs. the server's current text)
  is a correct, non-destructive three-way choice ("keep mine" / "take server's"), and
  `lockBlockers` genuinely recomputes from live manifest/field state on every render — no stored
  "resolved" flag exists for the lock gate to be tricked by.

17 is consistently honoured — no finding here involves a fabricated success, a silent data loss
path with no recovery, or a security bypass). The two severity-3 behavioural findings (7, 9) and
the two severity-3 cross-cutting findings (X1, X4) are the ones that must close before their
respective slice (UX02/UX05, and UX01 for the cross-cutting pair) certifies, per
`docs/design/UX_STANDARD.md` §4.2 ("Severity 3–4 blocks the slice; 2 needs a recorded decision").

Every severity-2 finding above is recorded here as the "decision" §4.2 requires: carried forward
into the named UX02–UX07 slice rather than re-litigated, since each already has a concrete,
scoped fix and none independently blocks certification of the *audit* itself (a docs-only,
no-code-change task).
