## FTF-0501-F2 — investigated, root cause confirmed, NOT claimed (needs a more careful fix than
## this shift's remaining budget allows to design safely)

PR #904 queued this as "ready": `direct_object_storage_upload.sniff_content`'s `_decodes_as_utf8`
check requires strict UTF-8 for any declared text-ish content type (jsonl/json/csv), so a
legitimately-encoded non-UTF-8 text file (the cp1256 CSV with an Arabic header that surfaced this
in FTF-H011-P1's own review) is wrongly rejected as `content_type_mismatch` — a false positive,
not a real ambiguous/unsupported file (FTF-0501's own §8.1 step 3/4 asks to "detect file type by
content" and "reject unsupported/ambiguous files", not to require UTF-8 specifically).

Root cause confirmed by reading `direct_object_storage_upload.py` directly (`_decodes_as_utf8`,
`sniff_content`) and the existing `tests/tasks/test_ftf_0501.py::test_n3_content_sniffing`. A
naive fix (drop the UTF-8 requirement, or fall back to "no suspicious control bytes" when UTF-8
decoding fails) was NOT implemented: it would silently flip the behavior the same test file already
pins at lines ~719-728 — a file whose content is TRUNCATED mid-UTF-8-sequence with `complete=True`
must stay `content_type_mismatch` (it IS malformed, not merely a different encoding), and a naive
"any non-control bytes are fine" fallback cannot tell that case apart from a genuinely-consistent
single-byte legacy encoding (cp1256, windows-1252, ...) using the same test's own fixtures --
both end in a byte with no control characters anywhere in the sample. Getting this right needs a
real way to distinguish "truncated valid-UTF-8 prefix" from "consistently non-UTF-8 single-byte
text" (e.g. confirming the decode failure is specifically at the very end of a byte sequence that
decodes cleanly otherwise, vs. scattered/early), not a quick patch -- and this item, unlike
FTF-R006-P1a's three findings, has only the one-paragraph description in PR #904's body, no
Control-plane-reviewed fix design to follow.

**Not parked in QUEUE.md directly** (relay PRs never edit QUEUE.md -- "No shared-file edits"
convention); disclosed here for Control plane to either rule on the intended fix shape or confirm
this needs its own round-2-style design decision before a relay session attempts it again.
**Three route options:**
1. Control plane specifies the exact distinguishing rule (e.g. "a decode failure only at the last
   1-4 bytes of a `complete=True` head, with no earlier invalid byte, is a boundary artifact, not
   a mismatch" or "try each of a short, explicit encoding list and require successful full-file
   decode under at least one, with the existing early-binary/null-byte checks staying the actual
   garbage filter") -- fastest path, matches how FTF-R006-P1a's return gave relay an exact ruling.
2. A relay session designs and proves the distinguishing rule itself in a PROVISIONAL PR, with the
   existing pinned truncation test as the regression guard and new cp1256/windows-1252 fixtures as
   the fix's own evidence -- slower, more relay-side judgment than usual for a security/correctness
   boundary, but workable under the "pick whichever option is most consistent with what is already
   decided elsewhere" default-resolution rule if no Control-plane ruling lands first.
3. Leave it queued as-is (no regression, no new risk -- the current behavior is only
   over-strict, not unsafe) until a future shift picks it up with a fresh budget.
