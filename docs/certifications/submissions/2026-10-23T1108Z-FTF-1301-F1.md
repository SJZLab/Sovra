## Round 1 — the described race

`apps/web/components/cost-and-model-search/costprofile_schema_ui.tsx`'s `refresh()` had no
ordering guard: a project switch fires a new `refresh()` while the previous project's request is
still in flight, and whichever reply arrives last wins, even if it is the stale one.

Fix: a `latestSearchRequest` ref counter, same `stale()` pattern already certified in
`apps/web/components/artifact-capabilities/capability_compatibility_ui.tsx` and
`apps/web/components/target-application/github_branch_ref_selector_immutable_sha_resolver.tsx`.
Every state-writing branch of `refresh()` (`!response.ok`, malformed body, success, `catch`,
`finally`) is guarded.

**Fault → RED table (round 1):**

| Fault | Test | Result |
|---|---|---|
| `stale()` always returns `false` (every guard defeated) | `FTF-1301-F1 a stale search response...` | RED |
| Only the post-`response.json()` `stale()` check removed | same | RED |
| Fix restored byte-identically | same | GREEN (19/19) |

Test: "FTF-1301-F1 a stale search response from the previous project never overwrites the new
project's result" (`apps/web/tests/ftf_1301.spec.ts`) — renders with project A, switches to
project B mid-flight, resolves B's reply first then A's (stale) reply last, asserts B's result
stands and A's never appears. Independently shown to FAIL on the pre-fix code (Law 1) before the
fix was written.

## Pre-review round 1 (independent, fresh reviewer, no prior context) — RETURN

The reviewer confirmed round 1's own fix and fault injection, then found a genuine second gap
beyond the item's own one-line description: `handleCreate`/`handleVerify` call `refresh(true)`
from the render closure current when the user clicked. If the project switches while that write
is still in flight, the closure's own `projectId` parameter is already stale by the time the write
resolves — the post-write refresh fetches the OLD project's search endpoint, and because it is
the *latest* call by the round-1 counter, its reply overwrites the correct, already-switched
project's panel. Reproduced with a throwaway jsdom probe (deleted after use): Verify clicked on
project A, switch to B, B's search resolves and renders correctly, then the Verify POST resolves
— the resulting 4th fetch targeted project A's URL, not B's.

## Round 2 — the post-write stale-closure gap

Fix: `identityRef` (`{ apiBaseUrl, organizationId, projectId }`), assigned directly in the render
body on every render (not inside an effect, so it is current before any already-in-flight async
callback resumes). `refresh()` now reads the identity it fetches with from `identityRef.current`,
never from the destructured props its own closure captured.

**Fault → RED table (round 2):**

| Fault | Test | Result |
|---|---|---|
| `refresh()` reads `apiBaseUrl`/`organizationId`/`projectId` directly instead of `identityRef.current` | `FTF-1301-F1 round 2: a Verify that finishes after a project switch...` | RED (4th fetch targets project A, test expects project B) |
| Fix restored byte-identically | same | GREEN (20/20) |

Test (same file): "FTF-1301-F1 round 2: a Verify that finishes after a project switch refreshes
the CURRENT project, not the one open when Verify was clicked" — Verify clicked on project A
(pending POST), project switches to B (B's own search resolves and renders), then the Verify POST
resolves; asserts the resulting post-write refresh call's URL is project B's, not A's.
Independently reproduced RED on the round-1-only code before writing the round-2 fix (Law 1).

## Pre-review round 2 (same independent reviewer, continued) — CERTIFY

Re-traced why the ref closes the gap (shared ref object updated synchronously in the render body,
read only after the resolved write, by which point a newer render has already updated it).
Additionally probed, beyond the producer's own tests:
- `handleCreate`'s own post-write `refresh(true)` path (not just `handleVerify`'s) — same fix,
  same result, passed.
- A→B→C triple switch with out-of-order replies (C first, then a stale A error, then a stale B
  success) — only C's result shows, no stale alert surfaces.
- Whether `handleCreate`/`handleVerify`'s own write requests (not the post-write refresh) have an
  analogous staleness exposure — judged not an issue: those POST to organization-scoped endpoints
  (no project ID in the URL), so a project switch mid-write does not change their target.
- Re-ran `vitest` (20/20), `tsc --build` (0), `eslint` on both files (0) — all clean.
- Fault-injected the round-2 fix itself (reverted the ref read to the bare closure params),
  confirmed the round-2 test went RED, restored byte-identically, confirmed GREEN.

Advisory (not blocking, noted by the reviewer): `refresh()` still reads `locale` from its own
closure, so a post-write error message could render in the previous locale if the UI locale
itself changes mid-write. Out of this item's scope (the item is about the project identity, not
locale); not fixed here.
