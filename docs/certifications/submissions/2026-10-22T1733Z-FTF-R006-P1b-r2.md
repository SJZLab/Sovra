## PR #968's verdict → this round's fix, one to one

1. **Cross-tenant workspace add** ("the store adds a member to an Argilla workspace before the database
   check, so an org1 annotator can read org2's dataset") → `_require_current_scope`
   (`argilla_identity_store.py:398`): re-fetches the `argilla_review_scopes` row by `scope.id` under
   `organization_id`'s own RLS scope and confirms `argilla_workspace_id` matches, called from
   `sync_workspace_membership` (`:469`) in the SAME initial tenant-scoped session as the existing identity
   check, before any real Argilla network call. A `scope` naming a foreign or non-existent row is refused
   with `ArgillaIdentityError` up front — symmetric with the stale-identity-reference guard that already
   existed.
2. **Revoke/sync race** ("a revoked identity keeps workspace access") → the plain read-then-write
   INSERT/UPDATE in `sync_workspace_membership`'s entitled branch is replaced with one atomic,
   identity-liveness-guarded UPSERT (`:471-501`):
   ```sql
   INSERT INTO argilla_workspace_members (organization_id, scope_id, identity_id, status)
   SELECT :org, :scope, :identity, 'active'
   WHERE EXISTS (SELECT 1 FROM argilla_reviewer_identities
                 WHERE id = :identity AND organization_id = :org AND status = 'active')
   ON CONFLICT (scope_id, identity_id) DO UPDATE
   SET status = 'active', updated_at = now()
   WHERE EXISTS (SELECT 1 FROM argilla_reviewer_identities
                 WHERE id = :identity AND organization_id = :org AND status = 'active')
   RETURNING id
   ```
   If a concurrent `revoke_reviewer_identity` lands in the window between the pre-call check and the real
   `client.add_workspace_user` call (which takes real wall-clock time), the `EXISTS` guard fails at write
   time and `written` comes back `None`; the function then calls `client.remove_workspace_user` to undo the
   real Argilla-side add it just made, and raises `ReviewerIdentityRevokedError` — never leaving a revoked
   identity with real external access.
3. **Concurrent `sync_workspace_membership` raises IntegrityError** → the same atomic UPSERT above resolves
   this for free: a concurrent winner's own INSERT no longer raises `IntegrityError` on the loser's side,
   it falls through to `ON CONFLICT ... DO UPDATE`.
4. **Table-wide UPDATE grant lets a revoked identity be restored** → new migration
   `0035_argilla_identity_hardening.py`: `argilla_review_scopes` loses `UPDATE` entirely (nothing ever
   updates it); `argilla_reviewer_identities` keeps `UPDATE` on exactly `(status, revoked_at, updated_at)`;
   `argilla_workspace_members` keeps `UPDATE` on exactly `(status, updated_at)`; a `BEFORE UPDATE` trigger on
   `argilla_reviewer_identities` refuses ANY update once `OLD.status = 'revoked'` (the same "terminal state,
   no further change is allowed" convention `0028_model_import_state_machine.py`'s own job-state trigger
   already uses). `revoke_reviewer_identity`'s own final UPDATE gained `AND status <> 'revoked'` so a
   legitimate concurrent double-revoke affects zero rows instead of ever reaching the trigger.
5. **Law 17 outage paths have no test** → `test_sync_membership_outage_on_add_is_never_swallowed` and
   `test_sync_membership_outage_on_remove_is_never_swallowed` (unit); confirmed the production code already
   propagated `ArgillaUnavailableError` correctly without a code change — these were a coverage gap, not a
   production bug.
6. **Never approved for omission: the real-Argilla CI job, the R002 `/validate` test, the compose stack and
   a gate step** → new CI job `argilla-real-server-integration` (`.github/workflows/ci.yml`), new test
   `tests/integration/test_argilla_real_server.py`, wired into `ci-verdict`'s `needs:`. See "Real-Argilla CI
   job" below — this is the one piece of this round's evidence that has not yet run for real.

## Real-Argilla CI job's first real run: found a real upstream bug, root-caused, fixed

The "unverified by a real run" section above is now out of date in one way: the job has run for real on
this PR (multiple times), and its very first real run found a genuine bug — exactly what disclosing it as
unverified, rather than quietly assuming it would pass, was for.

Every real run 422s on every single `GET /api/v1/status` call once the real argilla-server has a real
Elasticsearch wired up. First hypothesis (recorded in a since-superseded version of this file and the CI
job's own comment): version skew between the pinned `elasticsearch8[async] ~= 8.7.0` client library and
`elasticsearch:8.17.0`. Matching the exact `elasticsearch:8.8.2` version argilla-io/argilla's own CI tests
that client library against (commit `424eaa6`) did **not** fix it — the identical 422 recurred byte-for-byte,
disproving the version-skew theory.

Root-caused for real, not left as an open guess: `pip install argilla-server==2.8.0` into an isolated venv
in this sandbox (no Docker needed for this part — it's pure Python), then reproduced the exact exception
class from the CI logs (`pydantic_core._pydantic_core.ValidationError`) directly:

```
>>> from elastic_transport import ObjectApiResponse, ApiResponseMeta
>>> from argilla_server.api.schemas.v1.info import Status
>>> meta = ApiResponseMeta(status=200, http_version="1.1", headers={}, duration=0.1, node=None)
>>> oar = ObjectApiResponse(body={"a": 1}, meta=meta)
>>> Status(version="x", search_engine=oar, memory={})
pydantic_core._pydantic_core.ValidationError: 1 validation error for Status
search_engine
  Input should be a valid dictionary [type=dict_type, input_value=ObjectApiResponse({'a': 1}), input_type=ObjectApiResponse]
```

`GET /status`'s handler (`argilla_server/api/handlers/v1/info.py::get_status`) returns
`search_engine=await search_engine.info()` straight from `ElasticSearchEngine.info()` -> `self.client.info()`
(the `elasticsearch8` library), which returns an `ObjectApiResponse` — not a `dict`. The route's own
`response_model=Status` declares `search_engine: dict`. Under pydantic v2, that response-model validation
genuinely rejects `ObjectApiResponse` (confirmed: it is not a `dict` subclass — `ObjectApiResponse.__mro__`
is `(ObjectApiResponse, ApiResponse, Generic, object)`). The resulting `pydantic.ValidationError` (a
`ValueError` subclass) hits Argilla's own blanket `@app.exception_handler(ValueError)` -> 422. Confirmed
this has nothing to do with Elasticsearch's own version: a local repro against a fake ES double returning a
textbook-correct `GET /` response reproduces the same `ObjectApiResponse` wrapping regardless; the version
swap never touched the actual defect. Also confirmed NOT a logging red herring from
`argilla_server/_app.py`'s telemetry middleware (which the CI logs' own `WARNING: ... object has no
attribute 'code'` line comes from) — that middleware's `finally: return response` always returns the
original response untouched; its own `.code`-attribute `AttributeError` is a second, unrelated bug in
Argilla's telemetry client (`telemetry/_client.py:100`, `argilla_error.code` on an exception type that has
no `.code`) triggered by trying to log the *first* bug, not the cause of the 422 itself. Checked whether
this is already fixed upstream: it is not — `argilla-server==2.8.0` is still the latest version on PyPI, and
the identical `search_engine: dict` / `return await self.client.info()` pairing is still present on
`argilla-io/argilla`'s own `develop` branch as of this date.

This is a genuine bug in the real, pinned Argilla engine itself, not in Sovra's own adapter code (confirmed:
`ArgillaClient.get_status()` is defined but has no production caller anywhere in this repo — only this
round's own new real-server test used it against the real binary). Per CLAUDE.md's "seven reused
components" rule, Sovra owns the adapter/evidence layer around Argilla, never the engine itself — patching
the vendored `argilla-server` package is an ask-first fork of a reused component, not something to do
unilaterally. The fix stays entirely on Sovra's own side: added `ArgillaClient.get_version()` (`GET
/version` — returns only `{"version": ...}`, never touches the search engine, so this bug cannot reach it)
with its own wire-contract unit test (`test_get_version_wire`, self-attack-confirmed able to fail) in
`tests/tasks/test_ftf_r006_p1_client.py`; `tests/integration/test_argilla_real_server.py` now uses
`/version` for both its readiness-polling loop and the `compute_health`/`validate_component_binding` proof
(`compute_health` only ever checks for a 2xx response — see its own docstring — so `/version` serves that
proof identically to `/status` while sidestepping the bug entirely). `get_status()` itself is left as-is:
it correctly implements the real REST contract and has extensive pre-existing fake-server-backed coverage
from FTF-R006-P1/P1a; the bug is upstream, not in what it does. Its own docstring now documents the finding
for the next caller who might reach for it as a real-server health probe. Pushed as commit on top of the
PR; watching the next real CI run on `ci-verdict` to confirm this genuinely clears the job, the same
drive-to-green discipline as every other real CI failure this shift.
