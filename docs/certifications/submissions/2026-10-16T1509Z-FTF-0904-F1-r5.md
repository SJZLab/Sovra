### Finding 1 — QP-CASE-SPLIT-SEGMENT (production bug, fixed)

The existing last-word rule splits the name on separators AND on every camelCase boundary (a
lowercase letter immediately followed by an uppercase one) before comparing the last word. That
camel-boundary split can land *inside* a real separator-delimited segment that happens to be a
random-case spelling of a listed word: `mon_KeY` → the `e`-`Y` transition inside `"KeY"` splits
it into `"Ke"` + `"Y"`, so the last-word check only ever sees `"y"`, never `"key"`;
`status_CoDe` → `"CoDe"` splits into `"Co"` + `"De"`. The only remaining check, the deny-by-default
fallback, then lowers and strips separators from the *whole* name (`"mon_KeY"` → `"monkey"`,
`"status_CoDe"` → `"statuscode"`) and finds it on the closed `_BENIGN_NAMES` list, so it is
explicitly excused — by design, since `_BENIGN_NAMES` exists precisely to let `monkey=` and
`statuscode=` through as ordinary parameters. Live reproduction (pre-fix, on `uvicorn`):
`GET /x?mon_KeY=<v>`, `de_CoDe`, `zip_cOdE`, `status_CoDe`, `by_PaSs` all leaked the value.

Fix: a segment produced by an actual separator is never split further by case — it is looked up
lowered, as a whole, first. This only changes behaviour for separator-delimited segments whose
random-case spelling collides with a `_BENIGN_NAMES` entry when stripped-and-lowered; every other
case (plain camelCase with no separator, e.g. `sessionKey`; a separator segment that is NOT a
listed word, e.g. `foo_bar`) is unaffected, confirmed by the full existing round 1-4 suite (incl.
`test_f1_round4_closed_benign_list_and_non_endings_survive` / `..._never_excuses_a_credential...`)
still passing unchanged.

### Finding 2 — QP-NONASCII-PREFIX (test-coverage gap only; no production bug found)

The verifier's own round-5 return describes this as "the ASCII-only fallback fault stays GREEN" —
i.e. a *hypothetical* mutation that restricts the deny-by-default fallback to ASCII-only names
(`stripped.isascii() and stripped.endswith(...)`) was not caught by any existing test, because no
test used a non-ASCII prefix. I verified directly (`_is_query_param_name` traced by hand and by
running it live) that current production, unmodified since round 4, already redacts
`müllerkey=`, `étatcode=` and `中code=` correctly: none of `_QUERY_ASSIGN`'s `[\w.\-]` character
class, `_CAMEL_BOUNDARY`, `_NAME_WORD_SPLIT`, or the deny-by-default `stripped.endswith(...)` /
`.lower()` calls are conditioned on ASCII — Python's `\w` and `str.lower()` are Unicode-aware by
default. So this round needed a **test-only** fix: a generated table of non-ASCII-prefixed names
(`müllerkey`, `étatcode`, `中code`, `björkpass`, `françoissession`, `日本語sig`, `ñoñostate`,
`žluťoučkýkey`, each plain and upper-cased) pinning that they are redacted today, plus a new
`FAULTS` mutant that actually adds the `str.isascii()` restriction the verifier described — so a
future regression of this exact shape is caught.
