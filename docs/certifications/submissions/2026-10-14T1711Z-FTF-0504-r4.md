## Return items (round 3 verifier findings, all five addressed)

1. **V-RECORD-CAP-PROD-ONLY** (test only; production already correct) — the round-3
   "past the record cap" row (`x * cap + "," + y * (cap + 1)`) goes over by making the
   *second* field itself bigger than the per-field cap, so it also trips the per-field
   check on its own; it never isolated the record-level accumulation. Added a second row
   at the production constant: two fields exactly **at** the field cap, plus a third,
   **empty** field — no field individually over cap, but the record (two caps plus two
   separators plus a trailing comma and newline) is one byte over `2 * cap + 2`. Test:
   `test_size_boundaries_at_the_production_constants`.
2. **V-SHA-COMPARE-PREFIX** (test only; production already correct) — the existing
   mismatch test (`other = sha256(data + b"x")`) differs from the real hash almost
   everywhere, so a hypothetical prefix- or suffix-only comparison bug would still catch
   it by chance. Added `test_sha_mismatch_detected_at_a_single_hex_character`: flipping
   only the **first** or only the **last** hex character of an otherwise-correct hash.
3. **V-LOC-NONSTR-ALLOWED** (test only; production already correct) — added a case to
   `test_the_locator_lives_in_the_report_and_its_digest`: a `str` subclass instance whose
   *value* matches a valid, correctly-sealed locator exactly (`"line:7"`) is still refused,
   exercising `LocatedImportReport`'s `type(self.fatal_locator) is not str` exact-type
   check (the locator-grammar regex alone cannot tell a subclass from `str`).
4. **PREVIEW-SHA-TYPEERROR** (production fix) — `hmac.compare_digest` raises a raw
   `TypeError` on `None` or on a non-ASCII `str`. `ic.preview()`'s own internal
   accumulator always uses a valid, hardcoded dummy `expected_sha256`, so this crash was
   reachable only through `CsvEventStream._generate()`'s own comparison against a
   caller-supplied `dataset_sha256` — i.e. the preview path (and any direct `csv_events()`
   consumer), never through `run_csv_import` (whose `ImportAccumulator` already validates
   `expected_sha256` eagerly, separately, before this code runs). Fixed by validating
   `dataset_sha256` (exact type `str`, 64 lowercase hex) before calling
   `hmac.compare_digest`; a malformed value is `failed`/`source_changed`, same as a real
   mismatch, never a raw exception. Test: `test_malformed_dataset_sha256_is_a_typed_refusal_not_a_crash`.
5. **TRUNCATED-BOM-SWALLOWED** (production fix) — Python's own `utf-8-sig` incremental
   decoder buffers a strict prefix of its 3-byte BOM (`\xef` or `\xef\xbb`) and decodes it
   to `""` at end-of-stream *without raising*, unlike every other encoding in
   `CSV_ENCODINGS` and unlike `utf-8-sig` given any plain byte or a complete, genuine
   multi-byte truncation (verified empirically — see "Codec behaviour" below). A 1- or
   2-byte source declared `utf-8-sig` therefore looked like a trivially empty, valid CSV:
   `completed` with 0 records under `has_header=false`, or `mapping_column_missing` under
   `has_header=true` (both wrong — the source is corrupt/cut-off, not empty). Fixed:
   `_texts()` now raises `invalid_encoding` when nothing has been decoded yet (`first` is
   still `True`) and the reader consumed 1 or 2 total bytes under `utf-8-sig` specifically
   — the only state Python's own codec reaches by silently discarding non-empty input. A
   complete, genuine 3-byte BOM with no content after it is unaffected (still a legitimate
   empty source). Test: `test_truncated_bom_is_invalid_encoding_not_a_silent_empty_import`.

### Codec behaviour (why this is utf-8-sig-specific, empirically)
```
utf-16-le b'A'      -> final raises UnicodeDecodeError (truncated data)
utf-16-be b'A'      -> final raises UnicodeDecodeError (truncated data)
utf-8     b'\xc3'   -> final raises UnicodeDecodeError (unexpected end of data)
utf-8-sig b'\xef'   -> final returns '' silently (THE BUG)
utf-8-sig b'\xef\xbb' -> final returns '' silently (THE BUG)
utf-8-sig b''       -> final returns '' (correct: genuinely empty)
utf-8-sig b'ab'     -> decodes 'ab' immediately, no buffering (correct: not BOM-like)
windows-1256 b'A'   -> decodes 'A' immediately (correct: single-byte codec)
```
