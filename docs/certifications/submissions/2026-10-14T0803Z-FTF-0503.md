## Return items (0b)
1. **Whole-document `json.loads`, 62x memory** — fixed. `JsonContainerScanner` is a linear streaming byte scanner (string, escape,
   bracket-kind and depth state; compiled-regex jumps between interesting bytes). Each element is cut out alone and parsed by P1
   `strict_loads`. Peak for a 64 MiB container is within 1.5x of a 1 MiB one (`test_memory_peak_does_not_grow_with_the_container`);
   a 64 MiB single element peaks < 8 MiB; an ignored 1.5 MiB value is not retained; `json.loads` never sees more than one element.
2. **4301-digit int crashed the import mid-stream; duplicate keys, NaN, 1e999, lone `\ud800` accepted** — fixed: each is that
   element's row rejection (`number_out_of_range`, `duplicate_key`, `non_finite_number`, `invalid_unicode`), later elements import.
3. **A 3 MiB element accepted; an over-cap document lost every element** — fixed: an element over `max_record_bytes` is skipped by
   scanning without buffering and rejected `record_too_large`; the next element imports (max-1 / max / max+1 in 1-byte chunks).
4. **Content leaks** — fixed: rejections are `RowRejection(locator, code, slot)` only; fatals carry a byte offset and the mapping's own
   container pointer. Planted markers (value, key, bad element, role) appear in no report, locator, exception or log.
5. **No container mapping** — `json.container` is `"$"`, `"/<key>"` (other root keys must be in `ignored_top_level_keys`, else
   `unmapped_top_level_key`; ignored values are scanned, bounded and not retained) or `"$record"`; anything deeper is
   `mapping_unsupported`. Key match is exact on the decoded key (no casefold, no normalisation, `~0`/`~1` unescape).
6. **BOM refused, UTF-16/32 not `unsupported_encoding`** — BOM at byte 0 accepted (offsets count it); UTF-16/32 BOM or NUL among the
   first four bytes is fatal `unsupported_encoding`, decided before another byte is requested.
7. **No content-type gate, chunk input, ImportReport, Law 17 states, deterministic record id** — built on P1 `ChunkReader` /
   `ImportAccumulator` / `ImportReport`; only `application/json` imports; source outage is `blocked`/`source_unavailable`, a changed or
   truncated source `failed`/`source_changed`; `parse_timeout`, `too_many_rejections`, `source_too_large` all reported, never completed.
8. **Limits raisable / loosely typed; source labels reach metadata unmapped** — limits are P1 `ImportLimits` (lower-only, exact types);
   metadata comes only from the mapping's own slots; non-`key` slots, `csv` / `xlsx` blocks and a missing `json` block are refused up front.
9. **Named faults F2 (split at escaped quote), F3 (trailing comma), F9, F10** — both are in the table below and RED.

## Same-class sweep
- `jsonl_importer`: already on P1 (strict_loads per record, bounded buffer, same BOM/encoding/content-type/canonical-size rules) — nothing to fix.
- `csv_importer`: **canonical-size gap, not fixed here.** It has no `MAX_CANONICAL_RECORD_BYTES` check (`grep` finds none), so a CSV record that fits
  its field limits but whose ASCII-escaped canonical content is over 2 MiB is accepted and fails FTF-0508 later; JSONL and JSON reject it as
  `record_too_large`. It is FTF-0504's own module (pending certification; editing it here would invalidate that evidence, Law 15). Needs a Control-plane
  item.
- `xlsx_importer` does not exist yet (FTF-0505); the same rules apply to it when built.

## Disclosed
- Locator is `record:<1-based element ordinal>`; `record_index` is the 0-based ordinal. The fatal location is on the outcome
  (`fatal_locator` `offset:<n>`, `fatal_container`), like JSONL's, not an `ImportReport` field.
- Ignored root values and skipped oversize elements are checked structurally (strings, escapes, bracket kinds, depth, size) but not validated as JSON.
- `source_schema_sha256` is `None`. No live route calls the importer yet: `proving_symbol` stays blank; product-true stays 47/47.
- Over-long root keys (> 3,072 raw bytes, the longest a 256-character mapped name can be when fully escaped) are `unmapped_top_level_key` at once.
