## Mutation gate (diff mode, exactly as CI runs it: `--base origin/main`)

Iterative, as survivors turned up:

1. First run (174 mutants, test_ftf_0505.py + test_ftf_0502_p1.py): **166 KILLED | 8 SURVIVED | score 95.4%**, 2372.8s.
   - 3 survivors (`self.wanted is None` → `is not None`, SHARED/INLINE/LITERAL branches around
     `_bound_row_bytes`): genuine equivalent mutants. A mapped row's kept-cell total can never reach
     `MAX_HEADER_ROW_BYTES` (4 MiB) regardless of this condition, because `max_record_bytes` can only
     be lowered, never raised past its own 2 MiB default, and the shared `record_too_large` check in
     `_map_row` already rejects a mapped row whose fields add up past that — well under 4 MiB. Removed
     the dead conditional (same precedent as round 2's own equivalent-mutant finding: delete the dead
     code, don't allowlist); `_bound_row_bytes` is now called unconditionally for every kept cell.
   - 4 survivors in `_bound_row_bytes` itself (disable it / `if False` / `>` → `>=` / drop the raise):
     no test exercised the cap actually *firing*, only that memory stays low under it. Added
     `test_header_row_past_the_byte_cap_is_fatal_field_too_large`.
   - 1 survivor in `open_package`'s new except clause (item 4): no committed test, only a scratch
     repro. Added `version_needed_past_63()` as a new `test_archive_attack_table` case.
2. Second run (171 mutants — 3 fewer once the equivalent-mutant conditionals were removed):
   **170 KILLED | 1 SURVIVED | score 99.4%**, 2260.8s. The one survivor: `>` → `>=` on
   `_bound_row_bytes`'s own cap — the exact boundary was never pinned, only a value far past it.
   Added `test_header_row_byte_cap_is_exact` (three cells, each safely under the per-cell
   `max_record_bytes` default, summing to exactly `MAX_HEADER_ROW_BYTES` and to one byte over).
