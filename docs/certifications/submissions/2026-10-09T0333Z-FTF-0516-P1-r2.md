## Fix (QUEUE item 0l), mapped to the round-1 L2 return

1. **Real detector reports (both suites).** Both `_full_runs()` fixtures previously hand-built
   `RecordSchemaValidationReport(issues=(), ...)` and `TokenizationAnalysisReport(...,
   certifies_training_fit=True)` directly, bypassing the real FTF-0508/0509/0510 detectors
   entirely — and the finding showed the real FTF-0508 validator actually rejects all 5 fixture
   records (25 issues) once called for real. Fixed:
   - `_record_batch`/`_record` now also carry `schema_version` (FTF-0506's own `SCHEMA_VERSION`),
     `source_type`, `quality_status`, `pii_status` and `tool_schema_status` — the five Section
     6.11 fields FTF-0508's `validate_record_batch` actually requires — so the fixture is a
     record the real validator genuinely accepts, not a record it happens not to be asked about.
   - `record_schema` now comes from a real `validate_record_batch(batch)` call; an `assert
     record_schema.is_clean` on the fixture itself (not production code) makes a future fixture
     regression fail loudly instead of silently shipping a dirty report.
   - `tool_arguments` now comes from a real `validate_tool_calls([], locked_manifest={},
     current_tool_versions={}, instance_validator=None)` call (FTF-0509): an empty `tool_calls`
     sequence is genuinely `not_applicable` per that module's own contract, not asserted by hand.
   - `tokenization` now comes from a real `analyze_tokenization(batch, tokenizer=...,
     max_sequence_length=4096)` call (FTF-0510) against a real, **exact**
     `ChatTemplateFastTokenizer` — a real `tokenizers.Tokenizer` trained offline/in-memory on a
     tiny fixed corpus, with a real chat template, both pinned by their own real sha256 digests —
     the exact same technique `tests/tasks/test_ftf_0510.py` already established for its own
     suite (no network, no pretrained model). `analyze_tokenization` sets
     `certifies_training_fit = False` unconditionally whenever `tokenizer.exact` is `False`, so an
     *approximate* tokenizer (tried first, simpler) can never produce the clean report the slice's
     fixture needs — this is why the exact backend, with its template/digest machinery, is
     required here, not optional convenience.
   - An `assert tokenization.certifies_training_fit` on the fixture itself, same rationale as (1).

2. **Raw `sovra_app` CHECK negatives with positive controls (real Postgres, integration only).**
   - `ck_dataset_quality_reports_detectors_reported` (V11): a raw INSERT with
     `detectors_reported = ARRAY['bogus_detector']::text[]` is refused by the database with the
     constraint's own name in the error; a raw INSERT with a real detector name
     (`ARRAY['record_schema']::text[]`) is accepted (positive control, same org/dataset).
   - `ck_dataset_quality_reports_detector_versions` (V10): a raw INSERT with `detector_versions`
     missing one of the 7 required detector keys is refused by the database with the constraint's
     own name in the error; a raw INSERT naming all 7 is accepted (positive control).
   - Not added to the unit (SQLite) suite: both CHECKs use Postgres-only operators
     (`jsonb_exists_all`, array `<@`) SQLite cannot evaluate at all — a SQLite-side "test" of either
     would necessarily fake the enforcement, which is worse than not having one. The real,
     behavioral proof lives where the real enforcement lives (real Postgres), consistent with this
     migration's own existing raw-INSERT negatives (cross-tenant RLS, immutability trigger, FK
     CHECKs) which are likewise integration-only.
   - Independently confirmed outside the harness too: a direct `psql` raw INSERT with an empty
     `detector_versions` against the same migrated database reproduces
     `violates check constraint "ck_dataset_quality_reports_detector_versions"` verbatim.

3. **NUL-character / un-encodable-text input validation (production fix).** `_is_clean_text` —
   the one shared validator `idempotency_key`, each resolution's `reason`, and `list_issues`'s
   `detector` filter all already routed through — now also refuses a string containing a NUL byte
   (Postgres `text` cannot store one at all; psycopg previously raised a raw `DataError`, caught
   nowhere, surfacing as a raw 500) and a string holding a lone UTF-16 surrogate (cannot be
   UTF-8-encoded for the wire). Because all three call sites already shared this one function, the
   fix is a single, surgical change; no route or store call site needed editing. New tests (store
   level, no DB needed — the refusal happens before any SQL is built):
   - `submit_resolutions` with a NUL in `idempotency_key` → `InvalidResolutionRequestError`
     (`invalid_body`).
   - `submit_resolutions` with a NUL in a resolution's `reason` → same.
   - `list_issues` with a NUL in the `detector` filter → plain `ValueError` (the route already
     maps this to `400 invalid_filter`, confirmed by the pre-existing
     `"a store ValueError is 400 invalid_filter"` route test — untouched, no route code changed).
   - A positive control: a real detector name in the `detector` filter is still accepted.
