## Return items (all 5)

1. **Gate gap (production fix) — the most significant finding this round.** `verify_report` /
   `assert_leakage_clear` accepted a self-sealed report with `status="clear"`, `reason_code=None`
   and `methods_not_run` listing the 4 semantic methods: a forger with this module's own hash
   function (anyone who can read `compute_report_sha256`, which is not secret-keyed) can fabricate
   a report claiming "clear" while disclosing, in the very same report, that it skipped the
   semantic methods — and the hash alone, being internally consistent by construction, cannot
   refuse it.
   - **Why this is closeable, and closed:** `_derived_status`/`_REASON_STATUS` (unchanged this
     round) map every member of `FAILED_CODES`/`BLOCKED_CODES` to `"failed"`/`"blocked"`, so
     `reason_code is None` is the *only* way `status` can resolve to `"clear"` or `"leakage_found"`.
     `detect_split_leakage` only reaches `reason_code is None` by actually running every method
     (`run = (*HASH_METHODS, *(SEMANTIC_METHODS if semantic_ran else ()))`, and `semantic_ran` is
     exactly the condition under which no blocking reason gets set). So `reason_code is None ⟹
     methods_run == METHODS and methods_not_run == ()` is a real invariant of the real engine, and
     `verify_report` can mechanically enforce it. Added:
     ```python
     if report.reason_code is None and (
         report.methods_run != METHODS or report.methods_not_run != ()
     ):
         raise LeakageEngineError(
             "a clear or leakage_found report must have every method run and none skipped"
         )
     ```
   - **Why this doesn't overreach:** for every *other* reason code the real engine can set
     (`invalid_input`, a route code, `semantic_scan_saturated`, `finding_limit_exceeded`,
     `manifest_invalid`, `record_set_mismatch`), the legitimate `methods_run`/`methods_not_run`
     split varies (full, empty, or exactly the hash/semantic split) depending on *which* of those
     independent conditions fired — there is no single cross-check that covers every reason code
     without also covering, and possibly breaking, a legitimate partial-completion report. The
     fix is deliberately scoped to the one case that is both security-critical (gates real
     training/freeze decisions) and provably a closed invariant.
   - **Disclosed, not silently narrowed:** this closes exactly this one forgery class. Forging
     `methods_run`/`methods_not_run` on an already-`blocked`/`failed` report is not a safety gap
     — `assert_leakage_clear` never clears `blocked`/`failed` regardless of those two fields, and
     the status/reason/findings cross-check (unchanged, pre-existing) already refuses any
     internal inconsistency there.
   - **Spec-matrix correction:** `docs/spec-matrix.yaml`'s FTF-0518 notes claimed "refuses a
     report whose hash does not cover it (self-sealed forgeries too)" — true of a forgery that
     changes status/reason/findings without recomputing a consistent hash over them, but this
     round's own finding is a forgery that *does* recompute a fully consistent hash. Rewritten to
     say precisely what is and isn't covered (see the diff).
   - **Test:** `test_self_sealed_forgeries_are_refused` (`tests/tasks/test_ftf_0518.py`), new cases
     "leakage_found claiming the semantic methods were skipped", "clear claiming the semantic
     methods were skipped", "clear claiming nothing ran at all", plus two cases isolating `or` vs
     `and` between the two field checks (methods_run wrong alone; methods_not_run wrong alone) —
     the mutation gate's own second run found the combined-forgery cases alone left an `and` in
     place of the required `or` undetected (see "Mutation gate" below).

2. **F13 (test only; production already correct) — semantic work must never run before the route
   clears, not just go unreported.** The existing `test_route_profile_matrix` only checked
   *outcomes* (no semantic finding; `methods_not_run` lists the semantic methods), which cannot
   distinguish "never called `detect_near_duplicates`" from "called it, then discarded the
   result" — a materially different bug (wasted, and for an external route, policy-sensitive,
   computation against possibly-unauthorized content). New test
   `test_semantic_detector_is_never_called_before_the_route_clears` monkeypatches
   `sl.detect_near_duplicates` with a call-counting wrapper and asserts: **zero** calls across
   every refused-route reason (`security_profile_route_blocked`, `_route_not_authorized`,
   `embedding_provider_unavailable`, `security_profile_invalid_request`) and **exactly one** call
   for the internal route — reusing the exact route fixtures `test_route_profile_matrix` already
   established.

3. **F14 (test only; production already correct) — saturation counting must look at both sides of
   every pair, not one.** `detect_split_leakage`'s own `partners` dict increments both
   `candidate.batch_position_a` and `candidate.batch_position_b` for every near-duplicate
   candidate; no existing test forced a scenario where counting only one side would matter. New
   test `test_saturation_counts_both_sides_of_a_pair` builds a "hub" record (a prior
   `final_qualification` source, so — by `detect_split_leakage`'s own entry ordering, current
   records first, then prior sources — it always has the *largest* batch position of the group)
   that near-duplicate-matches 4 disjoint-vocabulary "partner" records which do **not** match each
   other. A direct fixture check against `detect_near_duplicates` (not just the full pipeline)
   confirms, empirically, the exact candidate graph: 4 hub pairs, 0 partner-partner pairs, and the
   hub is always the *larger* (`batch_position_b`) side — exactly the position a one-sided
   ("count only `batch_position_a`") counting bug would miss. At `max_semantic_partners=4` the
   scan saturates (the hub alone reaches the cap); at `5` it does not; at `3` it still does (the
   hub's own count, 4, is already over).
   - **Fixture construction, disclosed:** disjoint vocabularies alone were not enough — an earlier
     attempt using structurally-patterned "words" (shared digit/suffix patterns across different
     seeds) produced spurious partner-partner matches via character-5-gram shingle overlap,
     caught directly by the fixture's own "0 partner-partner pairs" assertion before this was
     submitted. Fixed by generating each partner from independent per-seed random lowercase
     letters (no shared structural pattern at all), confirmed empirically (not assumed) to
     produce exactly the intended candidate graph.

4. **F8 (test only; production already correct).** The existing "a duplicated record id is
   failed/record_set_mismatch" case (`[records[0], records[0]]`) also drops every other record
   from the 2-record fixture, so the pre-existing `set(ids) != set(assigned)` check alone already
   catches it — it cannot tell whether the *duplicate-length* check
   (`len(set(ids)) != len(ids)`) is doing anything. Added a case using the full record set plus
   one duplicate (`[*records, records[0]]`): the id *set* still equals `assigned`'s exactly, so
   only the length check can fire.

5. **LK-SATURATION, "a cap of 1 ... accepts either outcome" — pinned.** The fixture
   (`placed[:3] + placed[-2:]`) always includes the module's own canonical near-duplicate pair
   (`t`/`f`, built from `LONG_A`/`LONG_B`, a one-word paraphrase — the same pair
   `seeded_report()` and `test_each_method_detects_its_seeded_pair` already rely on being
   detected deterministically), so a cap of 1 is guaranteed to saturate on that pair alone,
   regardless of whatever else the 3 leading siblings do. Pinned to
   `one.reason_code == "semantic_scan_saturated"` (was `in (None, "semantic_scan_saturated")`).
