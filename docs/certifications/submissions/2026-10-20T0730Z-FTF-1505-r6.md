## Point by point (each named GREEN row -> the check that now turns it RED)

1. **LIVE-DECISIONS-UNPINNED.** `test_live_lane_decisions_fail_on_synthetic_captures` builds a
   correct capture: the startup line, one redacted access line per probe, and the positive control
   printed verbatim. That capture passes all `2 x probes + 4` checks. Each single defect then
   turns its own check red:
   - L1b: the startup line is missing.
   - L2: a 404 or 200 where 422/400 is expected, or no response at all.
   - L3: one probe's access line is removed (`family_x` must not be satisfied by `error_family_x`).
   - L4: no positive control.
   - L6/F15b: a canary, AWS or JWT leak beside the positive control. Each must fail
     `live_app_output_clean` and produce a blocking finding.
   - A run that never booted reports only a failed boot.

   `test_live_probe_table_targets_the_unauthenticated_error_paths` covers L2b/L2c. It pins the
   probe table: the 422 probe hits `/auth/callback` with no `code`; the 400 probes and every
   `error_family_*` probe hit `/auth/callback?code=`; every `family_*` probe hits a 404 route;
   and there is one error-path probe per rule family.

   `test_main_raises_when_a_live_result_fails` shows that `main()` raises on a failed live
   *result* that comes with no finding.
2. **DESIGN-FAULTS-AT-CALL-SITE.**
   - `test_rule_set_is_pinned` checks the rule set against a fixed reviewed list of 16 rules.
     Every seed must also be found as its own rule.
   - `test_history_lane_and_main_refuse_shallow_and_stale_baseline` checks that `scan_history`
     itself refuses a real shallow clone, and that `main()` itself raises on a baseline entry
     that matched nothing.
   - `test_main_blocks_on_every_rule_family_not_only_aws` puts one tracked seed per family in a
     repo; `main()` must name every rule as blocking.
3. **POINT-7-LANE-TRUNCATION.** `test_file_lanes_and_cli_scan_whole_long_lines_and_units` places a
   secret about 30 KB into one text line and about 80 KB into one non-UTF-8 unit. Both are found
   by `scan_source` and, once deleted, by `scan_history`. The CLI finds a secret 40 KB into one
   UTF-8 line.
4. **POINT-1/2-NAMED-CASES.** `test_long_base64_run_hex_after_many_runs_and_history_tgz` checks
   three cases:
   - a secret inside one 6,736-char base64 run;
   - a hex-wrapped secret after 3,000 other hex runs;
   - a history-only `.tgz` member.
