## Return items (0k), round 3

1. **EXPECTED-SHA-MISMATCH-COMPLETES** (binding catalog rule, 2026-10-13T23:59Z) — fixed. A caller could
   build the `ChunkReader` with one declared `expected_sha256` and then call `run_jsonl_import` /
   `jsonl_events` with a *different* `expected_sha256` (the value that tags every accepted record and the
   report itself). Only the reader's own end-of-stream byte check covered the reader's own value; the
   caller's separate value was never cross-checked against it, so a mismatched import could still
   `complete` and tag its records with a hash the bytes never had. `JsonlEventStream._generate` now
   compares the two with `hmac.compare_digest` before a byte is read (right after the content-type gate)
   and aborts `failed`/`source_changed` on a mismatch. Law 1: `test_expected_sha256_must_match_the_readers_own_declared_hash`
   shown RED by reverting only the production fix (`git stash` of `workers/data/jsonl_importer.py` alone,
   diff in the PR), then GREEN restored.
2. **FATAL-LOCATOR-OUTSIDE-IMPORTREPORT** — this round's own `import_common.py` edit for it (an additive
   `ImportReport.fatal_locator: str | None = None`, with its own P1-suite coverage) was superseded by a
   real merge conflict: FTF-0504 r3 (PR #786) merged first and had independently added the one shared
   mechanism to `import_common.py` ahead of the serialization ruling's own intended order —
   `ImportAccumulator.report(fatal_locator=...)` now returns a `LocatedImportReport` subclass when a
   locator is given (the base `ImportReport.fatal_locator` class attribute stays `None` otherwise, not a
   dataclass field there). Resolved by merging `origin/main`, taking its `import_common.py` as-is (the
   file is now byte-identical to `main`, zero diff), and dropping this round's own now-redundant
   `import_common.py` and `test_ftf_0502_p1.py` edits entirely (`test_ftf_0502_p1.py` is now
   byte-identical to its pre-round-3 state — confirmed by diff). `jsonl_importer.py` needed **no change**
   to accommodate this: it already called `accumulator.report(fatal_locator=...)` and exposed
   `JsonlImportOutcome.fatal_locator` as a property over `report.fatal_locator`, both already exactly
   compatible with the merged design. **Note for Control plane**: `test_ftf_0502_p1.py` was not extended
   to cover `LocatedImportReport` directly (only FTF-0504's own `test_ftf_0504.py` has
   isinstance/construction tests for it) — worth closing against whichever of FTF-0504 r3's or this
   item's own re-review it lands on.
3. **C4-MIDSTREAM-STOP-VACUOUS** (J4, integration) — fixed in
   `tests/integration/test_ftf_0502_jsonl_import_postgres_s3.py`: added a control run after the existing
   "stopping S3 mid-stream" check, on a dataset genuinely larger than the stopping run's own cutoff point
   (`index == 1`, a few MiB in) but sized to stay under this runner's own natural stream limit, through a
   chunk generator that never calls `compose stop`. **Real-infra confirmation, not just a disclosed
   limitation**: CI's own first run of this control (replaying the identical 96 MiB dataset, as this PR
   first wrote it) reproduced exactly the vacuity the finding describes — this runner's own SeaweedFS
   ended the "control" stream on its own at `source_bytes=25,300,625` (~25 MB) with **no stop call at
   all**, `blocked`/`source_unavailable`, confirming on real infrastructure (not merely asserted from a
   prior run's in-line comment) that the existing "stopping" check could not have been discriminating a
   real stop from this natural limit. Fixed by sizing the control dataset to 8 MiB — comfortably past the
   stopping run's own early cutoff, comfortably under the observed ~25 MB natural limit — so it completes
   cleanly (CI, run `38558658811`, job `jsonl-import-integration`, after this fix) while the stopping run
   still shows the real outage. **Disclosed**: this sandbox has no Docker daemon, so neither this nor the
   pre-existing suite could be run live here directly; CI is this module's real integration environment,
   and its own first run is what caught and corrected the original (too-large) control dataset choice.
