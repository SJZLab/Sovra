## Return items (0k), round 3

1. **EXPECTED-SHA-MISMATCH-COMPLETES** (binding catalog rule, 2026-10-13T23:59Z) — fixed. A caller could
   build the `ChunkReader` with one declared `expected_sha256` and then call `run_jsonl_import` /
   `jsonl_events` with a *different* `expected_sha256` (the value that tags every accepted record and the
   report itself). Only the reader's own end-of-stream byte check covered the reader's own value; the
   caller's separate value was never cross-checked against it, so a mismatched import could still
   `complete` and tag its records with a hash the bytes never had. `JsonlEventStream._generate` now
   compares the two with `hmac.compare_digest` before a byte is read (right after the content-type gate)
   and aborts `failed`/`source_changed` on a mismatch. Law 1: `test_expected_sha256_must_match_the_readers_own_declared_hash`
   shown RED by reverting only the production fix (`git stash` of `workers/data/jsonl_importer.py` alone,
   diff in the PR), then GREEN restored.
2. **FATAL-LOCATOR-OUTSIDE-IMPORTREPORT** (serialization ruling, Control plane) — fixed, the one shared
   `import_common.py` edit for the whole importer family: an additive `ImportReport.fatal_locator: str |
   None = None`. `body()` omits the key when `None`, so every report sealed before this field existed, and
   every scenario that still never sets it, hashes exactly as before (`test_rep_fatal_locator_is_additive`,
   `tests/tasks/test_ftf_0502_p1.py`, proves this directly: a report built with `fatal_locator=None` and
   one built the identical way before this round have the same digest formula; a report with a real
   locator hashes *differently*, proving the field is genuinely inside the digest when set, not a second,
   untracked field). `ImportAccumulator.report()` takes an optional `fatal_locator` kwarg.
   `JsonlImportOutcome.fatal_locator` is now a read-only property over `report.fatal_locator` (the
   dataclass field itself was removed) — every existing caller of `outcome.fatal_locator` is unaffected.
   `_drive()` passes `aborted.locator if isinstance(aborted, JsonlAborted) else None` through to
   `accumulator.report(fatal_locator=...)`. `test_utf16_utf32_are_fatal` gets a new assertion that the
   locator is reachable as `report.fatal_locator`, present in `report.body()`, and that `report_sha256`
   is genuinely the digest of that body.
3. **C4-MIDSTREAM-STOP-VACUOUS** (J4, integration) — fixed in
   `tests/integration/test_ftf_0502_jsonl_import_postgres_s3.py`: added a control run immediately after the
   existing "stopping S3 mid-stream" check that replays the identical 96 MiB dataset through a chunk
   generator that never calls `compose stop`, restarts S3 first, and asserts the import genuinely
   `completed` and read every byte. Without this, the existing "blocked/source_unavailable" assertion on
   the stopping run would still pass even if the real `compose("stop", "s3", ...)` call were made a no-op,
   because this suite's own prior runs have observed SeaweedFS end a sufficiently large, slow stream on its
   own well before the 96 MiB mark (documented in-line, ~21 MB). The control run proves the full stream
   does complete when nothing actually interrupts it, so the stopping run's blocked outcome is attributable
   to the real stop. **Disclosed**: this sandbox has no Docker daemon (confirmed: `docker ps` fails to
   reach the socket), so neither the pre-existing suite nor this addition could be run live here this
   round — same disclosed class as every other `*-integration` job in this repo. Syntax-checked
   (`ast.parse`), `ruff check`/`ruff format --check` and `mypy` clean. CI's `jsonl-import-integration` job
   is the authoritative first real run.
4. **Tables at the production constant** — added, `tests/tasks/test_ftf_0502.py`:
   - `test_size_boundary_at_the_production_limit`: max−1/max/max+1 at the real `DEFAULT_LIMITS.max_record_bytes`
     (2,097,152 bytes), not a reduced test limit.
   - `test_time_a_production_sized_record_in_one_byte_chunks_meets_a_budget`: a full 2 MiB record, one byte
     at a time, within a 30s budget (observed ~2s on this sandbox).
   - `test_chunking_every_offset_on_small_inputs`: every one of the ~600 single split points on a <=4 KiB
     mixed-fault fixture gives the identical report to the unchunked baseline, plus a fixed 7-byte chunking
     — exhaustive, not sampled, so a bug at one particular chunk boundary cannot hide between two random
     cuts the way `test_chunking_is_irrelevant`'s random sampling could.
   - `test_memory_ratio_is_tightly_bounded`: a 10x record-count increase (1,000 -> 10,000, after subtracting
     a 200-record baseline) stays within 1.5x of the 10x-scaled small-count overhead, tighter than the
     pre-existing 3x check.
5. **Report-field unit coverage** — added, `tests/tasks/test_ftf_0502.py`:
   - `test_rejection_slot_is_not_dropped` (**V-SLOT-DROPPED**): this file's own `codes()` helper (used by
     nearly every other check) only keeps `(locator, code)`, silently dropping `.slot`. Production code was
     already setting `.slot` correctly (GREEN); nothing here previously asserted it directly. Reads
     `RowRejection.slot` straight off the report for three different message-mapping rejections (each
     genuinely carrying `messages[0]`) and for a `record_too_large` rejection (which carries no slot at all,
     confirmed `None`, not an empty string or a repeated locator).

     `validation`, `development_eval` and `held_out_evaluation`, confirming each is carried into the report
     untouched, that the candidate record itself never carries a purpose field, that each purpose gives its
     own distinct `report_sha256`, and that an invalid value (`"Training"`) is refused, not coerced.
   - `evidence_hash` refreshed in `docs/spec-matrix.yaml` from round 2's `0ce7406e` to this round's code
     commit (see the PR for the final value).
