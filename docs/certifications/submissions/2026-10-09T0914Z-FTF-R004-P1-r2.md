## The six round-2 findings and their fixes

1. **Content-free capture.** `CONTENT_KEYS` (round 1) missed real content-bearing keys: Responses
   `instructions` and `prompt` template variables, chat `prediction`, legacy `prompt`,
   `conversation`, `previous_response_id`, and never scrubbed a nested `extra_body.messages`.
   Added the five missing top-level keys to `CONTENT_KEYS`. For the nested case, added
   `_scrub_content`, which recursively rebuilds any `Mapping`/`list`/`tuple` value, dropping any
   `CONTENT_KEYS` key at *any* depth -- so `extra_body: {"messages": [...]}` is scrubbed while
   `extra_body`'s other fields (e.g. `top_k`) survive (digest, not blanket-exclude, per the DoD's
   own "exclude or digest" wording).
2. **Exact comparison.** `_exact_equal` already did type-exact comparison (round 1), but had no
   regression test pinning "no implicit float tolerance" (F8) or "declared-value comparison uses
   the same type-exact helper, not plain `==`" (F10). Added both as explicit tests; no production
   change was needed for either (confirmed via Law-1 fault injection below -- introducing the
   faults the review named is what proves these were real gaps, not already-broken code).
3. **Bridge rewrite.** `approved=0.7, before=0.8, after=0.7` used to be `preserved` (only approved
   vs after was compared). Restructured the main loop: a key is preserved only when **both**
   `approved` (if present) and `before` (if present) agree exactly with `after`
   (`matches_approved and matches_before`). The approved-vs-before disagreement itself is now
   surfaced on the result (`approved_before_disagreement_keys`), never silently resolved by
   picking one side.
4. **Stale declaration.** A declared change naming a key that never appears in `after` at all, or
   whose `after` value does not exactly match what was declared, used to pass through unflagged
   whenever nothing else happened to touch that key (e.g. a declared `0.5` with the setting
   genuinely unchanged at `0.7`). Added a dedicated pass over every `declared_values` key,
   independent of the main dropped/changed/inherited loops, recording `stale_declared_keys` and
   folding it into `blocking_keys`.
5. **Reason codes.** Added `REASON_GENERATION_CONFIG_DROPPED`/`REASON_GENERATION_CONFIG_CHANGED`/
   `REASON_BRIDGE_DEFAULT_INHERITED` and a `reason_codes` field derived from which blocking
   categories are actually present (including the stale-declaration cases, folded into dropped/
   changed by whether the key was missing or mismatched). Added `compatibility_tuple_sha256` on
   the result, set only when the verdict is genuinely `declared_change`.
6. **Typed error / freeze / deep-copy.**
   - A `_MAX_NESTING_DEPTH` (64) bound threaded through both `_exact_equal` and the new
     `_scrub_content`'s own recursion, raising `GenerationConfigParityError` instead of a bare
     `RecursionError` on a cyclic or over-deep value.
   - `DeclaredGenerationChange.__post_init__` now freezes `changed_values` into a
     `MappingProxyType` over a deep-copied dict (`object.__setattr__`, since the dataclass is
     frozen) -- a frozen dataclass only blocks reassigning the attribute, not mutating the mapping
     object it points to; this was the real round-1 gap.
   - `capture_effective_generation_settings` now returns values built by `_scrub_content`, which
     deep-copies every leaf, so mutating the caller's own `request_body` after capture can never
     change the already-captured settings.
