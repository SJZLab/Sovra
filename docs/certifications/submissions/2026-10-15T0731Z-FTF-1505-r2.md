## Reproduced before any fix (Law 1)

Round 1's own module (`git show HEAD~1:tests/security/secret_scanning.py` before this round's
changes) restricted every lane to `SOURCE_ROOTS`/`ARTIFACT_DIRS` and the working tree:
`iter_tracked_files(root, dirs)` only ever listed files under its `dirs` argument, so
`tests/`, `scripts/`, `.github/`, `packages/*` and every root file were never scanned
(F-SCOPE), binary files and archive members were never opened (F-BINARY/F-ARCHIVE), no
decoding layer existed (F-DECODE), the history lane diffed `git log --all -p` (merge commits
never diffed by default -- F-HISTORY), the allowlist was keyed by raw value + file glob
(F-BASELINE), and the `quoted_secret_assignment` rule's `\b` boundary never matched
`db_password`/`client_secret`/`SECRET_KEY`, while a `your_`-prefixed value was waved through
unconditionally regardless of content (F-RULES). Each is reproduced directly in this round's
own test file as a RED check against the OLD behaviour before the fix (see each test's own
docstring), not merely asserted.

## Full rebuild (tests/security/secret_scanning.py)

1. **F-SCOPE (fixed):** `iter_tracked_files(root)` takes no `dirs` argument -- every
   `git ls-files` path is scanned, with no exclusion. `SOURCE_ROOTS` (now imported directly
   from `scripts/product_truth_check.py`, never a second hand-maintained list) is used only
   for the `assert_dirs_covered` coverage check, not to restrict the scan.
2. **F-BINARY (fixed):** `_scan_bytes` tries `utf-8` first (line-numbered, for real location
   evidence) and falls back to `latin-1` (a 1:1 byte mapping that never raises) for the whole
   blob when the content is not valid UTF-8 -- an ASCII-shaped secret inside a binary file is
   still found. All rule regexes compile with the `(?a)` ASCII flag; without it, Python's
   Unicode-aware `\b`/`\w` treat several Latin-1-supplement bytes (e.g. `0xFE`) as word
   characters, silently breaking the trailing boundary on a secret immediately followed by a
   high byte -- reproduced directly, fixed, re-verified.
3. **F-ARCHIVE (fixed):** `_iter_archive_members` extracts zip/whl/jar/egg and tar/tar.gz
   members, plus bare `.gz`, bomb-safe: declared member count and uncompressed size are
   checked BEFORE any member is read (refused over cap), and each member is then read bounded
   to `_MAX_SCAN_BYTES` regardless of its declared size.
4. **F-DECODE (fixed):** one layer of base64 (`[A-Za-z0-9+/_-]{24,}={0,2}` runs) and one layer
   of percent-decoding, both re-run through the full rule set. A cheap substring pre-filter
   (`_could_match_any_rule`) skips the expensive 15-regex re-check on a decoded candidate that
   contains none of the rules' own required literals -- performance-only, never a detection
   gap (every rule's required literal is in the filter list; proved directly in the test file).
5. **F-HISTORY (fixed):** `scan_history` no longer diffs `git log --all -p`. It scans every
   unique blob reachable from any ref (`git rev-list --objects --all` deduplicated by blob id,
   content streamed from one long-lived `git cat-file --batch` process). This catches a
   secret that enters history ONLY through a merge commit's own conflict resolution -- which
   `git log --all -p` never diffs by default -- reproduced directly
   (`test_history_finds_a_secret_introduced_only_in_a_merge_commit`: a real two-branch merge
   conflict resolved by typing a secret directly into the merge commit; `git log --all -p`
   on that real repo never shows it as an added line; `scan_history` still finds it).
   `assert_not_shallow` refuses a shallow clone outright (`git rev-parse
   --is-shallow-repository`), never silently narrowing to HEAD -- NOT_EXERCISED is a release
   blocker.
6. **F-ARTIFACTS (fixed):** `ARTIFACT_ROOTS` adds `reports/` to the existing
   `docs/certifications`/`docs/progress`. `assert_artifact_uploads_covered` parses every
   `actions/upload-artifact` `path:` out of `.github/workflows/ci.yml` and fails closed if any
   lies outside a declared root -- a newly added upload with no declared root is a release
   blocker, not a silent gap. This repo's own two real uploads (`reports/mutation-gate.json`,
   `reports/ci-verdict.json`) are both covered.
7. **F-LOGS (fixed):** `scan_log_samples` (the existing local-logger positive control, kept)
   is joined by `scan_live_app_log_samples`, which boots the real
   `uvicorn app.main:create_app --factory` (FTF-0904-W1 is installed and confirmed wired --
   `apps/api/app/log_redaction_setup.py` calls `install_api_log_redaction()` first in
   `create_app()`) and probes it with seeded shape-rule values and FTF-0905 canaries
   (literal/base64/hex/url/fragmented) carried in the query string, an `Authorization` header
   and a `Cookie` header, against a real 401 and a real 404 route, scanning the captured
   stdout/stderr. Disclosed scope: this lane exercises 401/404 only -- a live 5xx
   validation-error request path is not separately exercised (FTF-0904-W1's own suite already
   covers a startup-failure 5xx-shaped case; adding a live validation-error route was out of
   this round's own file set).
8. **F-BASELINE (fixed):** `secret_scan_baseline.yaml` replaces `secret_scan_allowlist.yaml`.
   Entries are keyed ONLY by `fingerprint: sha256(rule + NUL + value)` with mandatory
   `reason`/`reviewed_by`/`reviewed_on` -- `load_baseline` refuses an entry carrying a
   `value`/`path`/`file_glob`/`glob` key outright. `assert_baseline_fresh` makes a stale entry
   (one that matched nothing in the run) itself a blocking finding, so the file can only drift
   "too strict," never "too permissive." A fingerprint waives its (rule, value) pair
   everywhere it recurs, never scoped to one file (proved:
   `test_baseline_fingerprint_waives_every_recurrence_of_the_same_value`).
9. **F-SEEDS (fixed):** `scan_live_app_log_samples`'s canaries come from a fresh
   `generate_canary()` call at run time (FTF-0905); nothing is committed. The local-logger
   lane's `_default_seed_values()` stays a small fixed table of obviously-fake, baselined
   literals (same `CANARY-DO-NOT-USE`-style discipline FTF-0905 established) -- disclosed, not
   changed, since they are a positive-control fixture, not a leak-tracking canary.
10. **F-RULES (fixed):** `_QUOTED_SECRET_ASSIGNMENT`'s keyword alternation now uses a negative
    lookbehind (`(?<![A-Za-z])`) instead of a leading `\b`, so `db_password`/`client_secret`/
    `SECRET_KEY` (and any `_`/`-`-prefixed secret-named key) now fire -- Python's `\b` never
    matched inside a continuous `\w+` run like `db_password`. The `your[_-].*` placeholder
    bypass is removed outright: a high-entropy value prefixed `your_` is no longer waved
    through (`test_your_placeholder_bypass_is_removed`). Added rule families: `ASIA` AWS
    session keys, `aws_secret_access_key` pairing, GitHub PAT (82-char) and GitLab tokens,
    Slack webhook URLs, `sk-proj-`/`sk-ant-`/`rk_live_`, an `ENCRYPTED`/generic PEM header, a
    URL-userinfo password (placeholder-aware), a decode-based JWT validator (three base64url
    segments whose first decodes to a JSON object with `alg`, replacing the old
    `eyJ`-prefix-only regex), and the FTF-0905 canary shape (log/artifact lanes only -- a
    literal canary legitimately never appears in this repo's own source/history). The
    `quoted_secret_assignment` minimum literal length is raised to 20 and gated by FTF-0514's
    own Shannon-entropy threshold (`workers/data/pii_secrets_detector.
    _shannon_entropy_bits_per_char`, reused directly, >= 3.5 bits/char) -- round 1 had no
    entropy check at all.
11. **F-CI (fixed):** an additive `secret-scanning` job in `ci.yml` (`fetch-depth: 0`, no
    services) runs `tests/security/secret_scanning.py` directly as the live release gate
    (Section 53), added to `ci-verdict`'s own `needs:` list. No change to
    `scripts/ci_policy.py` or `tests/unit/test_ci_policy.py` was needed: both are already
    fully generic over every job `ci.yml` declares (`test_verdict_aggregates_every_job_in_ci_
    yml` asserts `needs == set(jobs) - {"ci-verdict"}` directly from the file), so the existing
    72 `test_ci_policy.py` checks enforce this job's wiring with no new test required.

against this repository's real tracked files/blobs, reviewed value-by-value before baselining

`tests/tasks/test_ftf_1505.py`/`tests/security/secret_scanning.py` -- discovered by re-running
the discovery scan against the actual committed tree (F-SCOPE means the source lane now scans

lane's full run matched was already covered by the source-lane baseline (same fingerprints).

Performance note: the first full-history attempt (pre-fix) was still running after 10+ minutes.
Profiled directly: a 2 MB blob's base64-decode layer alone was re-running the full 15-regex rule
set on up to 2,000 base64-shaped candidates (a 2 MB blob yields ~5,350 candidates matching the
`[A-Za-z0-9+/_-]{24,}` run pattern -- ordinary hex hashes/UUIDs/long identifiers, not secrets).
Added `_could_match_any_rule`, a cheap literal-substring pre-filter before the expensive re-check
-- every rule's own required literal is in the filter list, so it is a performance gate only,
