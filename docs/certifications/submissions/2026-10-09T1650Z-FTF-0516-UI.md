## What was built
`apps/web/components/dataset-factory/dataset_issue_resolution_ui.tsx` and `apps/web/tests/ftf_0516.spec.ts` (33 Vitest + React Testing Library tests, mocked `fetch`).
It consumes only the frozen FTF-0516-P1 routes: `quality-report`, `issues` (with `after` paging), `issue-resolutions`, `resolve-issue`.

* A decision carries the server's `quality_report_id`, `resolution_version` and, per issue, the server's `evidence_sha256` as `expected_before_evidence_sha256`; a stale view is refused by the server (409), never overwritten.
* Success is shown only when the response parses against the frozen schema (exact keys, sha256/UUID shapes, enums) AND echoes the report, issue, action and before-evidence that were sent. The screen then reloads, so state and version are the server's.
* Before/after evidence digests, actor and role come from the server's `DatasetIssueResolution`; nothing is inferred client-side.
* Every action, `waive` (the false-positive decision) included, needs a trimmed 1..2000 code-point rationale before anything is sent. `waive` is offered for a warning only. A detector failure and an already decided issue have no decision control. No control edits a record or locked dataset in place; the only write is `POST resolve-issue`, naming a successor dataset id the server validates.
* 400/403/404/409/5xx, network failure and a malformed or mismatched body are each an error, never success (Law 17).
* Identity: results and actions are tied to api/org/project/dataset; a switch clears the screen before the next commit and in-flight load/submit responses are ignored. The idempotency key is reused only for an identical retry that did not conclude, and dropped after success or `idempotency_key_reused`. A double submit sends one request.
