## Required items and the fix

1. **Run-level drift regardless of the completion tag.** `sync_run`
   (`reconcile.py`) only called `compute_run_drift` inside the
   `tags.get(TAG_PAYLOAD) is not None` branch, so a found run whose tag was
   deleted fell into the "never written" branch and was silently re-logged
   and re-tagged as SYNCED -- the exact bug the round-2 drift check was
   supposed to close. Fix: `compute_run_drift` now runs on every found run
   unconditionally, before any decision about whether to write. It is
   gated by the run's own terminal MLflow `status`
   (`FINISHED`/`FAILED`/`KILLED`, set only by this adapter's own
   `finish_run`, never a tag) rather than by the payload tag:
   - **Completed** (terminal status): every field must match exactly,
     including a field that went missing and a status that no longer
     agrees (`missing`/`changed`/`extra`/`status_changed`).
   - **Not yet completed** (status `RUNNING`, MLflow's own default, or a
     brand-new run): a field Factory has not written yet is not drift (it
     is about to write it), but a field already present that disagrees
     with what Factory is about to write is (`changed`/`extra` only, never
     `missing`).

   This single rule covers both findings without a separate tag-deletion
   special case: P1 (a completed run's own tag deleted, then a metric
   re-logged) is caught because the terminal status alone decides
   "completed"; P2 (a run tampered with before its own completion write)
   is caught because `changed`/`extra` are checked regardless of
   completion. A deleted tag with nothing else changed still heals back to
   SYNCED (the data agrees, so there is nothing to refuse).

2. **A CRLF/control-character bearer token crashed `sync_run` and leaked
   the token.** `MlflowClient._call` builds
   `headers["Authorization"] = f"Bearer {self._token}"` and hands it to
   `guarded_fetch`, which calls `http.client`'s own `conn.request(...)`.
   `http.client` validates header values and raises a bare `ValueError:
   Invalid header value b'Bearer <token>'` for an embedded `\r`/`\n` --
   reproduced for real locally (see Law 1 below). That `ValueError` is not
   `OutboundPolicyError`/`OutboundGuardError`/`OSError`, so it was not
   caught by `_call`'s `except` clauses, and it is not `MlflowClientError`,
   so `sync_run`'s own `except` clauses did not catch it either: it
   propagated out of `sync_run` entirely, carrying the raw token in its
   message. Fix: `_call` refuses a token containing a control character
   (`[\x00-\x1f\x7f]`) with a static message, before any header is ever
   built; a `ValueError` from the transport for any other reason is also
   wrapped as a static, scrubbed `TrackingRejectedError` (never the
   exception's own text, since a bytes-repr of a control character does
   not substring-match the live token the way `_redact` expects).

3. **`DurableOutbox.record` rewrote a row a concurrent sync had already
   resolved.** `record`'s final line, `row.attempt_count =
   entry.attempts`, ran unconditionally after every branch (SYNCED /
   PENDING / else), regardless of whether `record_sync_outcome` had
   already no-op'd because the row's real status was no longer `pending`.
   For the SYNCED/FAILED outcomes R002's own `record_sync_outcome` already
   guards `if outbox.status != "pending": return outbox` before touching
   anything -- but `record`'s own trailing `attempt_count` write still ran
   on the returned (unchanged) row (D3b). For the PENDING branch,
   `record_sync_outcome(outcome=None, ...)` on an existing row returns it
   untouched regardless of status (that path has no guard at all), and
   `record`'s own `last_error`/`updated_at` writes plus the trailing
   `attempt_count` write then stomped a row that something else had
   already resolved (D2). Fix: `record` now reads the row's current
   status first and returns immediately, touching nothing, when it is no
   longer `pending` -- a resolved row's status, external id, last_error
   and attempt_count all stay exactly as the concurrent resolution left
   them.

4. **Retry-due-time test strengthened (no production change).** The
   `World` row fixture in `test_ftf_r005_r3.py` previously had no
   `created_at` field at all, so a fault reading `row.created_at` instead
   of `row.updated_at` was only ever caught by an `AttributeError`, not a
   behavioural assertion. `World.row` now defaults `created_at` to a real,
   different value (`updated_at - 1h`); the existing due-time assertion
   now actually distinguishes the two, and a new explicit check
   (`R6-4`) asserts the due time is *not* `created_at + delay`.

5. **Law 2 corrections.** `docs/spec-matrix.yaml`'s round-2 notes claimed
   "never SYNCED or overwritten" and "scrubbed from every raised error"
   unconditionally; both were true only for the cases round 2 actually
   tried. Corrected in place with a dated note, rather than silently
   rewritten, plus this round's own paragraph. `evidence_hash` updated to
   this round's own commit (`b008bdc6`) -- prior rounds left it pinned to
   round 1's commit despite claiming new evidence.

Two of the 17 needed a second pass: `_UNSAFE_TOKEN_CHARS.search(...) -> if

applying each mutant to the file on disk and running the scenario directly
reproduced `TrackingRejectedError('MLflow request could not be sent')`
(the fallback's own static text) instead of
`TrackingRejectedError('token contains control characters')` (the explicit
check's own text) -- confirmed the file was restored byte-identical after
each (`diff` against a saved copy) before fixing the test to assert the
exact message rather than the exception type.
