Branch `relay/FTF-0505-r2`. Contract: QUEUE.md Active 0d (the Control-plane return of 2026-10-14T13:02Z).

## Return items

1. **ZLIB-ERROR-ESCAPES** — fixed. `read_part_blocks` (`workers/data/ooxml_safety.py`) now maps `zlib.error` to
   `xlsx_malformed`, alongside the exception classes it already mapped. A corrupt deflate stream inside any OOXML part
   (not its CRC, not its zip header — the compressed bytes themselves) previously raised `zlib.error` straight out of
   `run_xlsx_import`, uncaught. Tests: a unit-level mock (`BrokenZlib`, mirroring the existing `Broken`/`BadZipFile`
   test in the same function) and an end-to-end test that flips one real byte inside a real sheet part's own compressed
   stream and confirms the import completes `failed`/`xlsx_malformed` rather than raising.
2. **HEADER-ROW-UNBOUNDED-MEMORY** — fixed (the "until the header is found every cell is kept" defect; real repro: a
   single wide, deeply padded row placed before `header_row`'s skip count reached ~1 GB of real process memory from a
   roughly one-megabyte upload). Root cause: `_SheetScanner._finish_cell` only ever gated cell retention on `wanted`
   (the mapped-column set, set only once the header row is actually found), so every row the caller is still going to
   skip — because the header has not been reached yet — had every one of its cells' full text retained for no reason.
   Fix: `_SheetScanner` now takes the caller's own `header_row` skip count and tracks its own non-blank-row counter
   (`_non_blank_seen`), mirroring the outer loop's bookkeeping in `_sheet_events`; `_keep_full_row` is recomputed at
   the start of every row and gates retention, so a row still being skipped keeps nothing but its own blank/non-blank
   flag (needed to know when the skip count is satisfied) — never its cells' text. Verified both ways: confirmed a
   genuine ~1 GB real-RSS peak on the unfixed code via an isolated-process repro (built the attack payload to disk in
   one process, measured a *separate* process that only reads it — this matters, see "Methodology" below), then
   confirmed the fixed code holds the same scenario to under 1 MB of tracked peak.
3. **sharedStrings cap cost real memory disproportionate to its declared quota** — fixed, by the Control-plane-sanctioned
   "compact storage" option (ruling b: "compact storage or a lower cap"), not by moving or resizing the cap (that move
   into the shared `ImportLimits` is ruling (b)'s other half, deferred — see "Deferred" below). Root cause: `scanner.strings`
   held each shared string as a Python `str`, kept for the whole import (looked up by index, possibly many times, until
   the sheet is done). A `str` carrying even one non-Latin-1 character (routine in a multilingual workbook — Arabic,
   CJK, an emoji) widens that string's *entire* internal storage to 2 or 4 bytes per character, not only the wide
   character's own — so an ordinary multilingual shared-strings part cost up to ~3.8x its declared byte cap in this
   session's own isolated measurement (close to the "~3.4x" the return note names). Fixed: shared strings are now
   stored as UTF-8 `bytes` (no per-object width amplification), decoded back to `str` only once, for a string a cell
   actually references. Confirmed both ways with the same mixed-script-vs-ASCII payload at the same cap: before the
   fix, peak memory for the mixed-script payload was ~4x the ASCII payload's at an identical cap; after, the two are
   within noise of each other and both track the cap directly. A correctness round-trip test (café/emoji/Arabic
   through a real cell) pins that the decode-on-lookup path is exact.
4. **Fatal locator moved onto the shared report field** — done, matching the shape FTF-0504 r3 (#786, merged) already
   landed for CSV. `XlsxImportOutcome` drops its own `fatal_locator` field; `run_xlsx_import` passes
   `fatal_locator=aborted.locator if isinstance(aborted, XlsxAborted) else None` into `ImportAccumulator.report()`,
   which already builds a `LocatedImportReport` when given one (no import_common.py edit needed — that field already
   exists on `main`). Every test referencing the old `outcome.fatal_locator` now reads `outcome.report.fatal_locator`.
5. **Ruling (c), 2026-10-14T13:02Z** — both parts fixed:
   - `TargetMode="External"` is now compared after `.strip()`, not only `.lower()`: a value padded with leading/
     trailing whitespace (space, tab, newline) previously matched neither `"external"` nor "absent", bypassing the
     external-link refusal entirely. Pinned for five whitespace variants, all previously a bypass.
   - A vbaProject part reached only through a relationship `Type` (`.../relationships/vbaProject`) — never through its
     own part name (`MACRO_PART_PREFIXES`) and with no macro-enabled content type declared for it at all — is now also
     `unsafe_workbook`. Defence in depth: the existing checks only ever looked at the part's own name or its declared
     content type, never at how a relationship describes it.

## Methodology note: isolating a real memory defect from the test harness's own cost

Building the attack payload for items 2 and 3 (a near-gigabyte Python string, or tens of thousands of mixed-script
strings) is itself expensive in a naive in-process measurement — enough to dominate `resource.getrusage().ru_maxrss`
(a whole-process, monotonic high-water mark) and produce a false positive or false negative depending on what else the
same process already did. Two disciplines avoided this, matching the sibling `test_memory_is_bounded_by_the_row_not_
the_sheet` test's own existing pattern: either (a) build the malicious bytes to disk in one process and measure a
*separate*, fresh process that only reads them, or (b) start `tracemalloc` only *after* the payload is fully built
(so construction is never counted), and read its peak. Both new tests use (b); an early draft that used (a)'s own
cross-process ratio first confirmed the magnitude before the final in-suite tests were written this way.

## Mutation gate

Diff mode, as CI runs it (`--base origin/main`, `--test "uv run python3 tests/tasks/test_ftf_0505.py"`):
First run (200-mutant cap): `mutation_gate: 141 run | 139 KILLED | 1 TIMEOUT | 1 SURVIVED | 0 SURVIVED-allowlisted |
score 99.3% | 1917.6s`. The one survivor was `_SheetScanner.__init__`'s own
`self._keep_full_row = header_row <= 0` (M4: `<=` → `<`). Investigated rather than reported as-is: `_start_row`
unconditionally recomputes `_keep_full_row` at the start of *every* row, and a `<c>` cell is only ever reached
inside a `<row>`, so nothing ever reads the `__init__`-time value before `_start_row` has already overwritten it
— a genuine equivalent mutant, not a test gap. `docs/certifications/mutation-allowlist.yaml` is relay-forbidden
(CLAUDE.md), so the dead computation itself was removed rather than allowlisted: `_keep_full_row` is now only ever
assigned by `_start_row` (declared, not initialized, in `__init__`), eliminating the mutable expression the
survivor lived in. Re-run after that fix: `mutation_gate: 140 run | 139 KILLED | 1 TIMEOUT | 0 SURVIVED |
0 SURVIVED-allowlisted | score 100.0% | 1856.7s`. The one `TIMEOUT` in both runs is the same mutant (`read_part_blocks`, M2: `if not block: return` → `if False`,
`ooxml_safety.py:232`): dropping the EOF check means `handle.read(READ_BLOCK_BYTES)` returning `b""` forever
is never noticed, so the generator spins without end once a part is exhausted — the harness's own 300s per-mutant
timeout catches this as a real, live-tested fault (an infinite loop, not a silent pass), not a gap.
