## Fix

1. **Concurrent create, Law 17.** `create_backup` no longer accepts a `backup_id` parameter at
   all — it always generates its own via a new private `_new_backup_id()` seam (`str(uuid.uuid4())`).
   The real server (SeaweedFS 3.99) has no conditional (If-None-Match) write, so two concurrent
   calls that shared a caller-chosen id could let one caller observe a `BackupRecord` for a backup
   the other call's own later write makes immediately unverifiable (a second racing record
   version). Removing the caller's ability to choose the id at all removes the shared key two
   independent calls could ever collide on — the only robust fix once a conditional write isn't
   available. The CLI never exposed `--backup-id` on `backup` to begin with (only `verify`/`restore`
   take an existing id), so nothing in the CLI needed to change.
2. **Typed `now`, create and verify.** `created.tzinfo is None` → `type(created) is not datetime or
   created.utcoffset() is None` (and the matching change in `verify_backup`; `restore_backup`
   delegates its own `now` check to `verify_backup`, so it needed no separate change). A tzinfo
   that is set but whose `utcoffset()` answers `None` is treated as naive by Python's own datetime
   comparisons, so checking only `tzinfo is None` missed it.
3. **G1** (`_load_record` must read the exact pinned version, never "whatever is latest") and
   **G7** (the post-read re-list must compare identity, not only count) are round-4 code paths
   with no new production change this round — round 5 adds the real-SeaweedFS proof the return
   named as missing.

## Test-helper refactor (no production test-surface change)

Removing `backup_id` as a public parameter would have broken ~60 existing fixed-key assertions
across both test files that relied on passing a deterministic id straight through to
`create_backup`. Instead of rewriting every one of them to thread a dynamically-returned id, both
test files' own `run()`/`_backup()` helpers now take `backup_id` as their **own** fixture keyword
and patch the module's private `_new_backup_id` seam (`mock.patch.object(osb, "_new_backup_id",
return_value=backup_id)`) for the duration of the call. No real caller can reach this seam — it is
private, underscore-prefixed, and never imported by anything outside the two test files — so this
preserves the actual security property (`create_backup`'s real public signature has no `backup_id`
parameter at all) while keeping every pre-existing fixed-key test (`RECORD_KEY`, `"b1"` paths, the
round-4 `ExtraRecordVersion`/`MixedIdStore` fixtures) working unchanged.

Unit (`tests/tasks/test_ftf_1602.py`):

  and a `datetime` subclass, are both refused by `create_backup`/`verify_backup`/`restore_backup`.
- `test_round5_backup_id_is_always_generated` — `create_backup(..., backup_id="x")` raises
  `TypeError` (the parameter does not exist); two real calls with no forced id get distinct,
  non-empty ids.
- `test_input_validation`'s obsolete "slash in backup id" case removed (there is no longer a
  caller-facing `backup_id` to validate the shape of).

Real SeaweedFS (`tests/integration/test_ftf_1602_object_storage_backup.py`), replacing the old
`test_record_pin_race_and_existing_backup_id_on_real_server` (its R4-1 race scenario is kept,
renamed `test_record_version_pin_race_on_real_server`; its R4-2 "existing backup_id" scenario is
obsolete now that `backup_id` cannot be passed by a real caller at all):

- `test_concurrent_creates_never_collide_on_backup_id` — the primary real-world guarantee: six
  genuinely concurrent (`ThreadPoolExecutor`) `create_backup` calls, none passing or able to pass a
  backup_id, all succeed, all get distinct ids, and each independently and permanently verifies.
- `test_shared_backup_id_collision_is_never_silently_successful` — defense in depth: exercises
  Control plane's own named interleaving ("B checks the id, A runs in full, B writes") by forcing
  both calls onto the same id through the private test-only seam (the one thing a real caller can
  no longer do), confirming B never reports false success, and that a shared id would have left
  even A's own earlier "success" permanently unverifiable afterward — the real fix is that no two
  real calls are ever given the same id, not that the race can be made individually safe.
- `test_pinned_record_read_ignores_a_transient_unretained_swap` (G1) — first confirms directly
  against the real server that the genuine, COMPLIANCE-retained record cannot itself be deleted or
  replaced (a real `S3Error` 403/409 refusal), then proves the narrowest attack actually available
  — an unretained forged version briefly made "the latest" between the pinned listing and the
  pinned read, removed again before the re-list — is read around entirely: `verify_backup` returns
  the real, pinned record untouched. The fault (`get_latest` instead of the pinned version id) is
  shown reading the forged content via a local test-double that implements the fault directly
  (`FaultyLatestInsteadOfPinned`), independent of production — see "Fault → RED" below for why a
  global production-source mutation isn't the right way to prove this one.
- `test_record_relist_identity_swap_is_refused_on_real_server` (G7) — since the preceding test
  already confirms a genuine retained record cannot be swapped on the real server, this proves the
  re-list's identity comparison is load-bearing against the one input a less-trustworthy backend
  (or a future client bug) could still produce: a second listing reporting a different single
  "latest" version id. The first listing and the pinned read are real server calls; only the
  second listing's return value is substituted.

**Why G1's fault isn't proven the same way (reasoned, not a gap):** `_load_record` calls
`target.get_version(record_key, pinned_id)` by name. Globally replacing that call with
`target.get_latest(record_key)` in production source changes *which method the `ObjectStore`
abstraction dispatches to* — so the test's own `TransientSwap`/`FaultyLatestInsteadOfPinned`
classes, which inject the forged version from inside an overridden `get_version`, are simply never
invoked (production no longer calls that method at all), and the forgery never happens. Tried this
exact mutation directly to confirm: the suite stays green, for that reason, not because the attack
is actually closed. The correct, and already-applied, proof is the local test-double
(`FaultyLatestInsteadOfPinned`) directly implementing the fault's behavior and showing it reads the
forged `created_at` — confirmed both ways: the real (fixed) path returns the true value, the local
fault simulation returns the forged one, in the same already-passing run (see test output below).
