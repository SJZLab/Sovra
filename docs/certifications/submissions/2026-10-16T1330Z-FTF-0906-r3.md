## Point by point

1. **HISTORY-OPTIONAL.** `not_exercised` no longer depends on `required_stores`: without inspected
   `workflow_history` evidence the report is always `partial`. Test
   `test_history_is_always_partial_whatever_required_stores_says` (narrowed plan -> partial; real
   history -> passed; an `inspected=False` history record -> partial).
2. **CLIENT-UNOBSERVED-PASSES (Law 17).** `unobserved` on the client OR destination side gives
   `incomplete` with `client_unobserved` / `destination_unobserved` codes. Test
   `test_unobserved_on_any_side_is_incomplete` (deny and allow flows x three side combinations,
   flow and whole-report status).
3. **Unpinned clauses**, each a behavioural check (see table): F5b, F9, F10, F10b, F10c, F24, F25,
   F29 plus plan_id / status / policy_digest hash bindings. F10c is pinned by calling
   `_report_sha256` directly: through `verify_egress`, `not_exercised` and
   `"workflow_history" in inspected_stores` are now perfectly correlated, so an end-to-end pair
   cannot differ only in it.
4. **FABRICATED-INTEGRATION-EVIDENCE.** In the integration every `canary_found` is a real scan
   (`_scan` / `_scan_store_clean` over the bytes a sink actually received, the relay's real
   ciphertext, the real stores) or the `CanaryLeakedError` it raises; the leak-demo and bypass
   evidence use those values too. Enforcement decisions come from the exception TYPE
   (`OutboundPolicyError` = deny; `OutboundGuardError` after policy = allow + `reset`, not a deny).
   `assert_leak_test_complete` runs on the error-path, access-log (application_log) and artifact
   ledgers, and the leaking ledger is asserted to be refused. Flow D now reaches the H006
   cloud-metadata rule (port 80 and the address are both allowed by the test policy, so neither
   the port rule nor the allowlist rule can deny it) and the check requires that rule's message;
   flow C is likewise pinned to the explicit-allowlist rule. The test CA now carries
   basicConstraints/keyUsage (Python 3.13's default verification refused it).
5. **FRAGMENT-SCANNER-GAP.** A `fragmented` placement is found when the literal appears OR every
   piece of any 2..8-way split appears anywhere (any order, unrelated bytes between). Unit table
   over all split sizes (noisy, reversed, separate log lines, strict-subset negatives, another
   canary's pieces, literal placement not reassembling) and an integration request carrying ONLY
   `X-Canary-Frag-1/2` (contiguous literal absent from the bytes sink A received).
