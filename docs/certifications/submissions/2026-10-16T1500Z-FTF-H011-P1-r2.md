## Point-by-point

1. **MASK-LEAK.** The real design (QUEUE.md's own "Masking" bullet, read directly rather than
   reconstructed from the condensed return text: "every string leaf, header and key becomes
   `{"masked":true,"chars":n}`") was never implemented -- the shipped masking only covered a raw
   row's own *values*, using a size-bucketed string-prefix marker, and left the canonical
   candidate, `not_mapped`, `observed_role_values` and `ProbeResult.headers` all in clear, with
   headers/keys never masked at either way. Rewritten from scratch:
   - `_mask_marker(text) -> {"masked": True, "chars": len(text)}` -- the one shape every masked
     string becomes, carrying only a character count, never a size bucket or any fragment of the
     real text.
   - `_mask_leaf`/`_mask_candidate`: recursive value-only masking for structures whose own keys
     are this module's fixed schema names (the candidate document) -- `_mask_candidate`'s one
     disclosed exception is a `ContentPart`'s own `"type"` tag (`"text"`/`"json"`), which is
     schema, never raw content, and stays in clear exactly as `ComparisonCell.raw_type`/
     `canonical_type`/`identical` do (a separate field entirely, never masked at all).
   - `_mask_named_row`: a raw row's own header/key names ARE raw, uncontrolled source data, so
     Section 67.2's "header and key" clause applies to them too -- but a dict key must be
     hashable, and the masked marker is a dict, so it can never be one. A masked JSON/tabular row
     therefore comes back as an ordered tuple of `{"key"|"header": masked_name, "value":
     masked_value}` pairs, never a plain dict keyed by the real name (a disclosed, necessary
     adaptation to Python's own hashability constraint, not a silent deviation from the design).
   - `_mask_names`: masks `not_mapped`/`observed_role_values`/`ProbeResult.headers` the same way.
   - `preview_sha256` is computed from the real, unmasked candidate's own `record_sha256`/
     `normalized_sha256` (bound into the digest *before* masking is applied to the returned rows),
     so it stays identical regardless of `reveal` -- confirmed directly
     (`test_preview_sha256_deterministic_and_sensitive`, pre-existing, still green).
   - Tests: `test_mask_every_value_and_every_key_name`, `test_mask_candidate_type_tag_and_
     identical_flag_stay_visible`, `test_mask_rejected_row_candidate_stays_none` (a rejected row's
     own `candidate=None` masks as a safe no-op, never a crash), `test_mask_candidate_type_tag_
     exact_not_case_folded` (EXACT: a case-tampered `"Type"` key, white-box constructed, is never
     folded into the real `"type"` tag exception), `test_mask_not_mapped_and_observed_role_
     values_and_probe_headers`, `test_mask_tabular_row_pairs_with_headers`,
     `test_mask_nested_structures_and_scalars`, `test_mask_row_none_passthrough`. Integration:
     I1 rewritten to assert the new marker shape over every key and value, the candidate's own
     type tags/text masking, and `not_mapped` masking, against a real uploaded dataset.

2. **TOOL-VALIDATOR.** `run_mapping_preview` never accepted a `tool_argument_validator` parameter
   at all, so every tool-call row was rejected `canonical_schema_invalid` regardless of whether
   its own arguments were genuinely valid -- a tool-call-bearing source could never be previewed
   meaningfully, accepted or rejected. Added `tool_argument_validator: ToolArgumentValidator |
   None = None`, threaded straight through to the dispatched importer. `dataset_mapping_service.
   preview_dataset_mapping` no longer accepts `tool_schemas` as a caller argument at all (a
   caller-supplied override would let a stale or outright forged schema decide validation) --
   it now builds `tool_schemas` live from FTF-0404 `list_tool_definitions` on every call, and
   always passes FTF-0405's real `validate_instance` through. Test: `test_tool_argument_
   validator_threaded_through_to_the_importer` -- a real tool call, answered by a real tool
   result (matching `canonical_conversation_normalizer`'s own "every call must be answered"
   sequencing rule, reproduced directly against `normalize_conversation` first to get the fixture
   shape right): rejected without a validator, accepted with the real validator and a matching
   schema, still rejected with the real validator against a genuinely wrong-typed argument.
   Service-level wiring: `test_ftf_h011_p1_service.py` updated to patch `list_tool_definitions`
   and assert `tool_argument_validator is svc.validate_instance` by identity.

3. **SOURCE-CHANGED (Law 17).** A preview/probe reads only up to `limits.preview_max_records`
   rows -- fewer bytes than the whole object, by design. `ChunkReader`'s own size/sha256 check
   only ever fires at a real end-of-stream (its own docstring), which a preview that stops early
   never reaches, so an object tampered with past that point went completely undetected. Added
   `_drain_and_verify`: once the main read finishes (aborted or not), reads whatever bytes remain
   (within the same `reader.deadline`), forcing the real check to run; safe to call
   unconditionally, since an already-aborted `ChunkReader` just re-raises the same
   `ImportAborted` on every further read. Applied in both `run_mapping_preview` and
   `run_mapping_probe`. Tests designed so the tampered chunk sits *past* the loop's own natural
   one-event lookahead (the `for event in stream` protocol already has to pull one event beyond
   the limit to discover truncation, which would otherwise catch *some* tampering by accident and
   mask whether this fix is actually doing anything): `test_source_changed_detected_even_when_
   truncation_would_have_hidden_it`, `test_source_changed_detected_by_probe_too`. Integration: a
   real SeaweedFS overwrite (I7/I7b) -- a genuine >20-row dataset uploaded and verified, then its
   same S3 key overwritten directly with a longer tampered body, previewed and probed again,
   both asserted `failed`/`source_changed`. Not run locally (no Docker daemon in this sandbox,
   same disclosed limit prior H011-P1 and sibling-importer integration rounds recorded); left for
   CI.

4. **PROBE-LAW17.** `ProbeResult` carried only a bare `complete: bool` -- a storage outage or a
   changed object on the *probe* path had no visible verdict at all, unlike
   `MappingPreviewResult`'s own `state`/`failure_code`. Added the same two fields, same
   convention. Tests: `test_probe_state_is_source_unavailable_on_an_outage` (a real `OSError`
   from the underlying iterator -> `blocked`/`source_unavailable`, not a raised exception and
   not only `complete=False`), `test_probe_state_completed_on_a_normal_run`.

5. **`complete`'s own boundary bug**, in both functions (not separately named in the return, but
   directly implied by "complete means the whole source was seen... a 20-of-50 probe is not
   complete; an exactly-20-row preview is"): `len(rows) < limits.preview_max_records` can never
   be `True` once the limit is genuinely reached, so a source with *exactly* that many rows was
   always wrongly marked incomplete, indistinguishable from one truncated at the same count.
   Restructured both loops to check the limit *before* adding the triggering event (never
   counting, pairing or giving it a locator) and track `truncated` explicitly; `complete =
   aborted is None and not truncated`. Tests: `test_exactly_the_limit_many_rows_is_complete_not_
   truncated` (both functions) and its own flip side, `test_one_more_than_the_limit_is_
   truncated_not_complete` (proving LIM-6/7 are not simply always `True`).

6. **OBSERVER-COPY** (`import_common.py`, the one serialized edit this task's catalog rule
   allows). `apply_mapping`'s own `row_observer` tap handed the observer a *shallow*
   `dict()`/`list()` copy, which still shares every nested mutable value with the real row -- a
   nested-mutating observer could silently corrupt the very row `apply_mapping` was about to
   build the real candidate and hash from. First fix: `copy.deepcopy`, gated by the same
   `isinstance(Mapping) or (Sequence and not str/bytes)` guard the old code used. The first real
   local mutation-gate run (127 mutants, diff mode) found this guard's own `str`/`bytes`
   exclusion was now a genuine equivalent: since the fix already unified the copy mechanism to a
   single `copy.deepcopy(row)` call (rather than the old type-dispatched `dict()`/`list()`
   split), and `copy.deepcopy` is a documented no-op (returns the identical object) for the
   immutable `str`/`bytes` case, the exclusion no longer changes any observable behaviour for any
   reachable input -- removed it entirely, same resolution as FTF-0906's own `_hex64`
   finding (simplify away the now-dead mutation surface rather than disclose-and-wait on a
   Control-plane allowlist ruling). Tests: `test_observer_copy_is_deep_not_shallow` (direct,
   nested dict and list mutation), `test_observer_nested_mutation_never_changes_the_real_
   candidate` (differential, direct against `apply_mapping` -- never through `run_mapping_
   preview`/`run_mapping_probe`, both of which always install their *own* row-pairing tap via
   `_with_row_tap`'s own `dataclasses.replace`, which -- `row_observer` being a single field, not
   a chain -- silently discards any observer already on the mapping passed in; this was
   discovered empirically while first drafting this test through the full preview pipeline and
   finding the mutator was simply never called). Sibling suites (`test_ftf_0502_p1`,
   `test_ftf_0502`, `test_ftf_0503`, `test_ftf_0504`, `test_ftf_0505`) re-run clean after the
   `import_common.py` edit, confirming no regression (Law 15).
