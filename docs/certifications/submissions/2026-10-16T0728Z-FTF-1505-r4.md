## Point 2 -- F-LIVE-POSITIVE-CONTROL

`clean = not hits` passed just as happily over NOTHING as over a real, fully-logged request --
a live-app run where logging was entirely suppressed would still report "clean". Fixed:
`_access_log_evidence_present(captured, static_path, expected_status)` requires, for every probe,
a real access-log-shaped line (the probe's own static path -- never itself a secret -- together
with the real status code) somewhere in `captured`; its absence is now its own failing
`ScenarioResult` (`live_app_access_logged_<name>`), proven directly against uvicorn's own
`get_path_with_query_string`-based access-log format (confirmed by reading the installed
`uvicorn==0.31.1`'s own `protocols/utils.py`: the full path+query string, unredacted by uvicorn
itself, is what reaches the stream before this process's own logging config redacts it).

Second half: round 3's own docstring claimed "every route reachable here requires auth ... a
5xx/422 validation-error path stays unreached" -- false. `apps/api/app/auth/oidc_login.py`'s
`/auth/callback` has no auth dependency (it IS the login flow); `code`/`state` are required,
un-defaulted function parameters. Two new probes added to `_build_live_app_probes`:
`/auth/callback?state=x` (missing `code` -> FastAPI's own request validation -> 422) and
`/auth/callback?code=x&state=x` (no valid transaction cookie ->
`{"error": "invalid_or_expired_login_transaction"}`, 400) -- both read directly from the
handler's own source, not guessed.

## Point 3 -- F-ARCHIVE-ZLIB

A corrupt DEFLATED zip member's `handle.read()` raises `zlib.error` (not `zipfile.BadZipFile` --
that only fires on a CRC mismatch AFTER a successful decompress), which round 3's own per-member
except tuple did not list. It escaped the member loop, hit the function's own outer bare
`except Exception: return`, and silently abandoned every member after the corrupt one -- the
exact class round 2's own CRC-mismatch fix was supposed to close, reopened one layer down.

Reproduced directly (`test_f_archive_zlib_corrupt_deflate_member_does_not_abort_later_members`):
a real 3-member `ZIP_DEFLATED` archive with the middle member's compressed bytes corrupted at the
deflate-stream level (`BFINAL=1`, `BTYPE=0b11`, deflate's own reserved/invalid block type --
`zlib.error: Error -3 while decompressing data: invalid block type`, confirmed empirically before
writing the test). Fixed: `zlib.error` added to both the zip and tar member-read except tuples
(same-class sweep, CLAUDE.md), plus the archive-open except tuples (point 4). GREEN: all 3 members
enumerated, the corrupt one `None`, `good2.txt` still read. RED (fault reproduced): the OLD
except tuple (no `zlib.error`) abandons `good2.txt`.

## Point 4 -- F-ARCHIVE-CORRUPT/OVERSIZE

**4a (open failure).** A truncated `.zip`/`.tar.gz`/`.gz` fails at the OPEN call itself
(`zipfile.BadZipFile`, `tarfile.ReadError`, `EOFError`) -- the same outer bare
`except Exception: return` swallowed this with NO signal at all, treating an unreadable archive
as if it had zero members. Fixed: each archive-type branch now opens inside its own try/except;
on failure it yields one `(_ARCHIVE_SENTINEL_NAME, None, False)` row, which
`_scan_content_and_members` turns into a blocking `scan_incomplete` finding (same mechanism
per-member failures already used). GREEN/RED in
`test_f_archive_corrupt_open_is_a_blocking_scan_incomplete_finding` (truncated zip AND truncated
tar.gz, both via `_iter_archive_members` directly and via the real `_scan_content_and_members`
caller).

**4b (oversized member).** `handle.read(MAX_SCAN_BYTES)` alone cannot distinguish "member was
exactly the cap" from "member was truncated to the cap" -- unlike the top-level per-file/blob
bound (`_read_bytes_bounded`'s own `truncated` flag), no archive-member read ever signalled this.
Fixed: `_iter_archive_members` now reads `MAX_SCAN_BYTES + 1` bytes and yields a `(name, data,
truncated)` 3-tuple; `_scan_content_and_members` raises a blocking `scan_incomplete`
(`"(member exceeds scan bound)"`) when `truncated`, in addition to still scanning the bounded
content. GREEN/RED in `test_f_archive_oversized_member_is_a_blocking_scan_incomplete_finding`.

The `_iter_archive_members` yield type changed from `(name, data|None)` to `(name, data|None,
truncated)` everywhere (zip/tar/gz); the two round-3 tests that unpacked 2-tuples
(`test_corrupt_archive_member_does_not_abort_later_members`,
`test_archive_member_bomb_safety_caps`) are updated to the 3-tuple, their own assertions
unchanged.

## Point 5 -- F13-SEAM

Round 3's own 200-char/150-char-step overlapping-window chunking (a 50-char overlap) missed any
match longer than 50 chars positioned to straddle a window boundary -- several rule patterns have
NO upper length bound (`{20,}`, `{36,}`, the JWT segments' `{10,}`), so no finite overlap is
provably `>=` the longest possible match. Fixed: `secret_rules._matches_long_line` now calls
`_matches` directly on the whole line -- no windowing at all. No rule pattern in this module nests
a repeated group inside another repeated group (the shape that causes catastrophic regex
backtracking), so this is safe on an arbitrarily long single line.

`test_f13_every_offset_in_a_long_line_is_found_no_seam_gap` sweeps EVERY third offset across a
420-char padded line (140 offsets) for two long-match rules (`aws_secret_access_key`'s own full
match, keyword+value+quotes, ~65 chars; `slack_webhook`, ~81 chars via an unbounded `{20,}` run):
GREEN -- the real, fixed `scan_line` misses 0/140 for either rule. RED (fault reproduced) -- a
local reimplementation of round 3's own overlapping-window algorithm (not touching production)
misses >=1 offset for both. The pre-existing, narrower
`test_f13_long_line_window_finds_a_secret_past_the_200_char_boundary` (one hand-picked offset,
AWS access key ID) is kept unchanged -- it still passes under whole-line matching.
