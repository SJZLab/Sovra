## Point by point

1. **B64-RUN-LENGTH-CAP.** `test_secret_straddling_base64_run_length_boundaries_is_found` encodes
   a secret inside one base64 run of about 9 KB. It places the secret's encoding at 142 start
   offsets across the 4,096- and 8,192-character boundaries, covering every alignment mod 4.
   Every placement must be found. Capping `_BASE64_RUN` at `{24,4096}` or `{24,8192}` turns the
   test RED. On the 4,096 cap it misses starts 4029-4034 and beyond.
2. **HEX-RUN-LENGTH-CAP.** `test_secret_deep_inside_one_long_hex_run_is_found` places a hex-wrapped
   secret 680, 6,000 and 60,000 hex characters into one hex run. Capping `_HEX_RUN` at `{16,512}`
   or `{16,4096}` finds no run at all, so the test turns RED.
3. **LIVE-CALLSITE.** `test_real_live_lane_decides_on_observed_statuses_and_the_real_capture` boots
   the app for real twice:
   - **First boot:** it adds a probe that expects HTTP 418, a status the app never returns.
     - That probe must fail with the observed status 404, and every other status check must pass.
     - A spy on `_live_decisions` must see uvicorn's own output: `Started server process [pid]`,
       `Waiting for application startup.` and the extra probe's real access line.
   - **Second boot:** uvicorn's stderr is dropped. The app must still boot, and
     `live_app_stderr_captured` must fail.

   Three call-site faults each turn the test RED:
   - passing the expected statuses (`{p[0]: p[5]}`);
   - appending `_STARTUP_LINE` to the capture;
   - building its own capture.
