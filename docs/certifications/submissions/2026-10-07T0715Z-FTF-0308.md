## Gap vs. the packet

The task packet's own `files` list names only `apps/web/components/artifact-capabilities/
model_to_artifact_mapping_ui.tsx` and `apps/web/tests/ftf_0308.spec.ts` — frontend-only. But
`training_capability_classifier.py` (FTF-0307) requires a real `AliasReconciliationResult`
(no default) and an already-resolved `TrainableArtifact`, and its own docstring states there is
"no persisted alias-to-artifact binding anywhere in this repository's schema" — the caller must
supply which artifact maps to which model_id explicitly. No existing route exposes this
composition. Per Section 84.3 ("refine any oversized item... reuse an existing compatible
module") and the identical precedent FTF-0214's own docstring already set for the same class of
gap, this submission adds one new endpoint to the already-CERTIFIED, already-wired
`app.litellm.model_catalog_routes.build_model_catalog_router` (FTF-0214's own file) — no new
router-build function, no schema change (honoring this task's own `database_changes` clause).

## New route

`GET /api/v1/organizations/{organization_id}/connections/litellm/{connection_id}/models/{model_id}/training-capability?artifact_id=<uuid>`

Composes, in order: `get_connection` (FTF-0201) → `discover_models`/`enrich_visible_models`/
`reconcile_aliases` (FTF-0204/0205/0207, reused verbatim from `GET .../catalog`, never
reimplemented) → `get_artifact` (FTF-0301, tenant-scoped) → `classify_training_capability`
(FTF-0307). A revoked connection, or a discovery that never reaches `DISCOVERED`, falls back to
a real, honest empty `AliasReconciliationResult` rather than skipping the call.

## Real relevant integration — a genuine defect caught only by Postgres

The first integration run raised a real `sqlalchemy.orm.exc.DetachedInstanceError`: the
`TrainableArtifact` row fetched inside `tenant_scoped_session_for(...)` was read again
(`classify_training_capability`/`_serialize_artifact_provenance`) after that `with` block closed
the session. The no-DB suite's `SimpleNamespace` fixture never expires, so it could not have
caught this — only the real database did. Fixed with `session.expunge(artifact)` before the
`with` block exits; re-ran against the same local PostgreSQL 16 instance, all checks passed.
