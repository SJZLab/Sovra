## 1. MISSING-BROWSER-TEST

`apps/web/tests/browser/ux05_entry.tsx` extended:
- `mount()` now keeps a single persistent `Root` per page (`root ??= createRoot(...)`) and calls
  `root.render(...)` on every call, so a second `mount()` with new props (a different `projectId`)
  is a genuine React prop-change re-render of the already-mounted component instance — not a fresh
  mount of a new one, which would not reproduce a race inside that instance's own in-flight
  closures. No existing test is affected: each Playwright `page` is its own fresh JS realm, so
  `root` starts `undefined` again every time, and every existing state still calls `mount()` exactly
  once per page.
- A new `Route.hold` flag: a held request never resolves until the test calls
  `release(index, status, body)` (0-based, in the order each `hold: true` route was first matched).
  Unlike `pending` (never resolves), this lets a test control the *arrival order* of several
  requests in flight at once. The two requests in the new test are distinguished by the project id
  embedded in their own path (`/projects/<id>/costs/cost-per-success/search`), matching the real
  app's own URL contract — not by call order.

New test (`apps/web/tests/ftf_ux05_browser.spec.ts`, describe block "FTF-1301-F1 round 2: out-of-
order project-switch race (real Chromium)"): mounts project A (held), switches to project B (held)
via a second `mount()` call into the same root, releases B's reply first (renders "Project B
cheapest"), then releases A's (stale) reply last — asserts B's result stands, A's never appears,
no uncaught exception or unhandled rejection.

**Fault → RED table:**

| Run against `dab64d2^1` (pre-round-1 production code, no `stale()` guard at all) | RED — "Project B cheapest" count 0 (the stale A reply, arriving last, overwrites it) |
| Run against `dab64d2` (round-1-only code, merged) | GREEN — round 1's own fix already closes this exact race |
| Run against the round-2 head (this branch) | GREEN |

## 2. STALE-WHILE-LOADING

Root cause: the round-1 fix stops a stale *response* from overwriting state, but did nothing about
the previous project's already-rendered state sitting on screen under the new project's own loading
indicator until its response arrives (or forever, if it hangs).

Fix (`costprofile_schema_ui.tsx`): an `identity` key (`apiBaseUrl`/`organizationId`/`projectId`) and
a `seenIdentity` state, reset *synchronously during render* (never in an effect, so there is no
committed frame showing the old project's rate under the new project's loading state) — the same
`seenIdentity` pattern already certified in the sibling `capability_compatibility_ui.tsx`
(FTF-0309). On any identity change: `search`, `error` and `notice` are cleared and `loading` is set,
before the mount/identity-change effect even fires its own `refresh()`.

New tests:
- jsdom (`ftf_1301.spec.ts`), "STALE-WHILE-LOADING": switch project while the new request is still
  pending — asserts the old project's rate is gone and the loading indicator is shown, the instant
  the switch commits.
- Chromium (`ftf_ux05_browser.spec.ts`), same assertion via the real mounted component.

**Fault → RED table:**

| Fault | jsdom | Chromium |
|---|---|---|
| `seenIdentity` reset drops the four `setSearch(null)`/`setError(null)`/`setNotice(null)`/`setLoading(true)` calls | RED | RED |
| Fix restored byte-identically | GREEN | GREEN |

Both independently confirmed RED on the pre-round-2 (round-1-only, `dab64d2`) code before writing
the fix (Law 1).

## Advisories

- **P8 (severity 2, "fix if cheap with the same guard")**: fixed in both `handleCreate` and
  `handleVerify`. Each now captures `const clickedIdentity = identity;` before its own `await`,
  and guards its own write's error-branch `setError` calls with
  `identityKey(identityRef.current) === clickedIdentity` — a 409 (or any other) error from a
  Verify/Create clicked on project A no longer surfaces once the user has switched to project B.
  Two tests: "P8" (Verify) and "P8, Create" (Create — added after the pre-review's own probe found
  the Create-side guard, present in the first push of this round, had no test exercising it; forcing
  `stillCurrent()` true in `handleCreate` alone turned nothing RED until this test was added). Both
  independently fault-injected (guard removed → RED; restored → GREEN). The create-success *notice*
  (`costProfileCreated`) is deliberately left unguarded — it is organization-scoped, not
  project-scoped, and still a true statement regardless of which *project* is currently displayed;
  only guarding error surfaces is in scope here, matching the advisory's own wording.
  **Disclosed gap, not fixed (reviewer's own further probe):** the same `identityKey` also changes
  on an *organization* switch, which this notice's guard does not distinguish from a project
  switch — so on the (currently hypothetical, since nothing in this UI switches organization
  mid-session yet) path where organization does change, "created" could show under the new
  organization's panel for a write that was truly created under the old one. Recorded as an
  advisory for Control plane to weigh, same treatment as the `locale` item below, rather than
  adding an organization-only identity key to a UI path that cannot currently exercise it.
- **`locale` read from a stale closure**: not fixed this round — recorded again as out of this
  item's scope (the item is about identity, not locale), consistent with round 1's own submission.
