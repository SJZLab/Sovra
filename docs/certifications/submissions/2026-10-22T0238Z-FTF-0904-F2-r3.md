## Finding -> change -> test

### Point 2: F2-ESCAPED-QUOTE-FORM (production fix)

`_QUERY_ASSIGN`'s `qsep` group required a *literal* `"`/`'` immediately after the separator
(`(?=["'])`). A JSON-escaped key (`\"state\": ...`) or an escaped opening value quote
(`state=\"V\"`, logfmt `msg="... code=\"V\" ..."`) left that lookahead unmet, so the WHOLE match
(the key included) was skipped by `_QueryParamRule.sub` -- a total leak of both the key and the
value, not a truncation. Reproduced directly against `main` before any change:
`lr.redact_text('state=\\"Zq7...\\"')` returned the input unchanged.

**Change** (`packages/security/log_redaction.py`):
- `qsep`'s own leading part gained `\\*` before the optional key-closing quote, exactly mirroring
  `_SEP` (already used by the `_HEADER`/`_KEY_VALUE` rules): `\\*["']?[ \t]*[:=][ \t]*`.
- `qsep`'s lookahead became `(?=\\*["'])`: it now also accepts a backslash run before the value's
  opening quote, but does NOT consume it -- left for `_QUOTED_SECRET` to match, the same split
  `_SEP` + `_QUOTED_VALUE` already use.
- `_QUOTED_SECRET` gained two new LEADING alternatives (one per quote style) that mirror
  `_QUOTED_VALUE`'s own escaped-open branch: a possessive backslash run (`(?<!\\)` for one start
  per run), the opening quote, content that is plain chars or a backslash run NOT immediately
  followed by the matching quote (so a `\"`/`\'` pair inside the content is reserved for the
  terminator, never content), then the closing delimiter -- a backslash run THEN quote, OR a bare
  quote with zero backslashes, OR end of line/string if neither exists (fail closed; see the two
  pre-review fixes below for why the closing side needed two more rounds). The two existing
  bare-quote alternatives are unchanged, byte-for-byte, and kept LAST and ADJACENT (an existing
  round-2 fault anchored to their adjacency; preserved by ordering the two new alternatives first
  instead of interleaving them).
- `_QUOTED_VALUE` itself is untouched, as this round's scope requires.

**Test**: `test_f2_r3_escaped_quote_form_is_redacted` (a generated table, escape levels 1-3,
independently applied to the key's own closing quote and to the value's quotes, every quote
style, both separator forms) and `test_f2_r3_escaped_quote_form_live_json_and_logfmt` (a
JSON-object shape, a logfmt wrapper, and two bare-name sanity cases), both via `redact_text` and
the real logging path.

**Scoping disclosure (independently found, not asked for; a Control-plane ruling is needed)**: the
table above excludes `_F2R2_SECRET_NAMES` (password/token/api_key/client_secret/secret) and two
`_F2_NAMES` entries ("jsessionid", "access.token_sid") that substring-match `_SECRET_KEY_WORDS`
("session"+"id"; "token"). Those names are caught by the untouched `_HEADER`/`_KEY_VALUE`/
`_QUOTED_VALUE` path FIRST, which has its own pre-existing gap (no escaped-open alternative for
single quotes, only double). The round-3 DoD both (a) asks every F2 name -- "jsessionid" included
-- to be fixed, and (b) forbids touching `_QUOTED_VALUE`. These conflict for exactly the two names
above, in the single-quote escaped-open shape only (`jsessionid=\'V\'`, `{\'jsessionid\': \'V\'}`);
the same generic names (password/token/...) have the identical gap. Not fixed here either way;
flagged for a ruling: (i) authorize a future round to add a single-quote escaped-open alternative
to `_QUOTED_VALUE` (parity with its existing double-quote one), or (ii) accept this exclusion as
the scope boundary. The BARE (non-escaped) form of every one of the 13 names is unaffected and
fully redacted (confirmed directly, and independently by the L2 pre-review round 1, and by the V17
pin's own fault choice: dropping "jsessionid" from `_QUERY_PARAM_NAMES` is an equivalent/
non-observable mutant precisely because the generic rule already covers its bare form -- "ticket"
was used for the V17 fault instead).

**Second disclosure (found by L2 pre-review round 3, pre-existing, not a regression)**: a
DOUBLY-escaped inner quote inside a value (e.g. a generic `password`-keyed value containing its own
escaped quote, `password=\"SEC\\\"RETV\"`) ends the match at the inner escaped quote, leaving the
remainder (`RETV`) unredacted. Reproduced as byte-identical on `main` before any of this round's
changes and on the generic `_QUOTED_VALUE` path -- the same documented backslash-run/termination
design this whole module uses throughout, predating every round of this item. Not fixed, not in
scope; recorded for Control-plane awareness only.

### Point 2 (L2 pre-review round 1 finding): escaped-open value with no closing escape anywhere

Pre-review round 1 (a fresh reviewer subagent) reproduced a real leak in this round's own new
code: an escaped-open value truncated mid-line or at end of input (a cut-off log line, e.g.
`{\"state\": \"V`, no later `\"` anywhere) made the WHOLE escaped-open alternative fail to match
at all (it required a genuine closing backslash-run-then-quote), so the match was skipped
entirely (key included) and the value printed raw.

**Change**: both new escaped-open alternatives gained a fail-closed ending,
`(?:X|(?=[\r\n])|\Z)` -- the same shape round 3's own `_QUOTED_VALUE` fix (#940) already uses for
its own bare-quote alternatives -- so a value with no later escaped close runs to end of
line/string instead of failing to match. **Test**:
`test_f2_r3_escaped_open_with_no_closing_escape_fails_closed`.

### Point 2 (L2 pre-review round 2 finding): escaped-open value closing on a bare (unescaped) quote

Pre-review round 2 found the first fix was still incomplete: an escaped-open value is ALSO
correctly terminated by a BARE quote with no backslash at all -- e.g. a truncated escaped JSON
value inside an outer logfmt-quoted message (`msg="...code=\"V"`, the outer wrapper's own closing
quote). The prior fix's closing backslash run required at least one backslash (`\+`), so this case
still fell through to end-of-line, over/under-redacting past the real boundary.

**Change**: the closing backslash run in both escaped-open alternatives is now `\*+` (zero or
more, possessive) instead of `\+` (one or more). Not a new ambiguity: the content loop's own
backslash-alternative already excludes any backslash run immediately followed by a quote from
content, so there is still exactly one terminator-eligible position per value, whatever number of
backslashes (including zero) precede it. **Test**:
`test_f2_r3_escaped_open_closes_on_a_bare_quote` (both quote styles, the reviewer's own two
reproduction strings, tail-preservation checks).

L2 pre-review round 3 (final, holistic) ran 20 of its own adversarial probes against the combined
fix (multiple bare quotes in a row, mixed backslash counts, an F2 value and a generic
`password`-keyed value on the same line, cross-quote-style content, nested JSON truncated at
different depths, zero-length values, CRLF-embedded values, performance on 60K+ char pathological
inputs) -- 19/20 redacted cleanly with no leak and no catastrophic backtracking (worst case
0.135s); the 20th is the pre-existing doubly-escaped-inner-quote gap disclosed above, confirmed not
a regression. Verdict: **"FTF-0904-F2-r3 CERTIFY"** (evidence for this submission, per Law 4 never
a certification itself -- the real L2 certifier is a separate Control-plane session).

### Point 5: over-redaction record (Control-plane decision, not a defect)

Independently measured (methodology: every value in each corpus, placed as `{name}="{value}"` for
every one of the 13 base `_QUERY_PARAM_NAMES`, scanned with the current `redact_text`):

| Corpus | Size | Distinct values swept | (value, name) pairs redacted |
|---|---|---|---|
| Common first names (John, Maria, Ahmed, ...) | 40 | 40/40 | 520/520 |
| Glued/compound names (JohnSmith, MacDonald, ...) | 16 | 16/16 | 208/208 |
| Ordinary English words (running, finished, ...) | 30 | 30/30 | 390/390 |

Every value in every corpus is swept, for every name, with no exception -- the rule does not
inspect the VALUE at all, only the KEY's shape, so it cannot distinguish a secret from
`{"state": "running"}` (the module's own previously-certified-benign example, independently
reproduced: `redact_text('{"state": "running"}')` -> `'{"state": [REDACTED]}'`). Per the
Control-plane's own recorded ruling (QUEUE.md item 0b, point 5): "a quoted VALUE after a
credential NAME is redacted by design (fail closed beats a readable status)" -- recorded here as a
measurement, not treated as a defect to fix.
