recorded: `noticeImported`'s English-only `{plural}` hole, since Arabic needs no plural suffix).

The reviewer's own **F8** ("save `.json()` try/catch removed, unpinned") and **F19/F24/F29**
("each signal bump removed, but the mechanism is never shown to be load-bearing") deserve a
different fix than a forced pin. Investigating F19/F24/F29: every one of the three top-level
`raiseXError` call sites starts its own `loadPage`/`handleImport`/`handleSave` by clearing its
error to `null` as the very first synchronous statement, before the request has even started —
so the alert component always fully un-mounts (the conditional render sees `null`) and a brand
new instance mounts once the failure actually lands. Mounting itself already re-runs
`FocusableAlert`'s focus effect; the `signal` counter the round-2a submission sold as load-bearing
was unreachable dead weight given this control flow, exactly as the reviewer's fault injection
showed. **Removed** the `signal` prop and the three per-operation signal `useState`s entirely
instead of adding a fake pin for something that was never real — `FocusableAlert` now simply
focuses once on mount (`useEffect(() => ref.current?.focus(), [])`), which the existing "repeat
failure" test still exercises and still passes, honestly this time. (F8 — the save
`.json()` try/catch — was in fact already covered: `ftf_ux06.spec.ts`'s existing
"a non-JSON 200 on import shows..." class of test has a save-specific sibling
("a malformed-200 save response never claims a field needs fixing", added for P5 below); the
reviewer's own fault (F8) is the same code path this test's fault-injection pass (below) confirms
independently.)

**P5 (WRONG-RECOVERY-STEPS):** the single fixed recovery suffix per region was wrong whenever the
failure wasn't actually a field/content problem. Added a `RecoveryKey` ("recoverList"/
"recoverImport"/"recoverSave"/"recoverRestricted"/"recoverRetry") threaded through each
`raiseXError(message, recoveryKey?)` call: a 403 (`restrictContent()` fires) now says "Ask an
evaluator or administrator for access." instead of "press/fix and retry"; a transport failure
(the request never reached the server) or a malformed/non-JSON response on import or save now
says "Try again." instead of claiming a field needs fixing. A genuine field-validation failure
(the common case) keeps the original "fix the field/file and try again" phrasing.

**P6 (STATIC-IDS):** **not fixed — recorded as a scope boundary, not fixed by omission.** Every
`field-*`/`*-error`/`*-field-errors` id in this component is a literal string the CERTIFIED,
byte-identical `ftf_0602.spec.ts` suite itself hard-codes via `document.getElementById(...)`
(e.g. `"field-category-error"`, `"field-severity-error"`). Scoping these with `useId()` would
require editing that certified parent suite's own assertions to match the new generated ids —
which is both outside this round's own file set (`evaluation_case_editor_import.tsx`,
`strings_0602.ts`, `ftf_ux06*.spec.ts`) and in direct tension with the parent's own
"byte-identical" requalification claim this round (and round 1) depends on. This is a genuine
two-instances-on-one-page collision risk (disclosed, not hidden) that a future round owning
`ftf_0602.spec.ts` itself would need to resolve together with the id scheme.
