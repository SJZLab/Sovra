## Desired / observed / enforced — the real mapping used

- **Desired**: `forbidden_actions_json.actions[].name` — the mandate's own declared forbidden-action list, edited
  here as a structured list (add/remove by name + reason), not raw JSON.
- **Observed (repository contract)**: the live `/requirements` view's own `is_critical`/`requires_confirmation` per
  tool, matched to a forbidden-action name by `ToolDefinition.name`. Section 7A.7's own example ("repository tool
  schema permits `refund`, while user mandate says refunds are forbidden") is exactly `reason: "not_declared_critical"`.
- **Enforced (observed runtime contract)**: the same view's own `runtime_enforced` field — Section 66.4's own "User
  saying 'refunds forbidden' does not prove runtime denial."

`evaluateForbiddenAction`/`evaluateForbiddenActions` are pure functions of only those two already-live sources.
`mandateLockBlockers` reports exactly the two reasons that are genuinely unresolved
(`not_declared_critical`, `not_runtime_enforced`) — `not_found` (no discovered tool yet) is disclosed, not asserted
either way, and `enforced` is never a blocker.

## Negative acceptance: "User override cannot declare a dangerous runtime safe; unresolved policy conflicts block lock"

- No control in the component writes a resolved/acknowledged/safe flag for a forbidden action — asserted directly
  by scanning every rendered `<button>` for forbidden wording (`safe|acknowledge|accept risk|resolve|dismiss|override`).
- The conflict is recomputed from `requirements` on every render; `handleSave`'s own PATCH response updates only
  `manifest`, never `requirements` — saving a mandate edit cannot double as resolving a conflict.
- The only way a conflict clears is "Refresh enforcement status", a separate, explicit, read-only `GET
  /requirements` — and only when it returns genuinely different data (tested both ways: same data → conflict
  stays; changed data → conflict clears).
- "Unresolved policy conflicts block lock": a `mandate-lock-blocked`/`mandate-lock-ready` banner, driven by the
  same pure `mandateLockBlockers`, so a later manifest-wide lock gate (FTF-04A23, which lists this task as its own
  dependency) can consume the identical computation instead of re-deriving it.
