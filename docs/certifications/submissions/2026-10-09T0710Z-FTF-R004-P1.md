## Design decisions (first round for a new slice -- no prior review to answer to yet)
- **CONTENT_KEYS exclusion, not an allow-list.** The acceptance text names specific settings keys
  by name ("temperature/top_p/token/reasoning settings") but also says "any unknown settings key,
  kept verbatim" -- read together with "reads only the settings keys ... never messages or tools",
  the safer reading for "do not silently drop configuration" is a generous capture (everything
  that isn't a known content/identity key) rather than a narrow allow-list that would itself
  silently drop a bridge's new sampling parameter. `CONTENT_KEYS` names exactly what is excluded:
  `messages`, `input`, `tools`, `functions`, `function_call`, `model`, `stream`, `user`,
  `metadata`.
- **`approved` takes precedence over `observed_before` on disagreement.** The acceptance text's
  own ordering ("approved or before") and `approved` being the one value the candidate
  configuration actually locked. Recorded in the module docstring as a "Recorded reading" per the
  repo's default-resolution-rule convention, since this is a genuine ambiguity in the slice's
  own text, not a Control-plane-answered question yet.
- **`GenerationParityResult` holds only key names, never values**, even though the compared
  *values* are generation settings, not prompt content -- the literal DoD text ("never prompt
  content") is satisfied by construction either way, but key-names-only also means a bug that
  mistakenly captured content would still not surface it through the result, a second line of
  defense beyond `CONTENT_KEYS` alone. `DeclaredGenerationChange.changed_values` is the one place
  values are kept, because they are the candidate's own declared values, not captured content.
