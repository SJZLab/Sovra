## E (write)

**`packages/integrations/argilla/client.py`** (new, pure, stdlib-only). `ArgillaClient`:
`get_status`, `list_workspaces_me`, `create_workspace`, `ensure_workspace` (idempotent: find by
name, create if absent, resolve a create-race via one re-list rather than a retry loop),
`list_workspace_users`, `add_workspace_user`, `remove_workspace_user`, `create_user`, `get_user`,
`delete_user`. Four error classes kept apart so a caller can never turn one outcome into another
(Law 17): `ArgillaUnavailableError` (network/timeout/5xx -- retryable, never success),
`ArgillaRejectedError` (understood-and-refused, or a malformed/duplicate-key/non-finite/
wrong-shape response -- never retried as-is), `ArgillaNotFoundError` (404),
`ArgillaConflictError` (409, the outcome `ensure_workspace`/a future `create_user` caller
branches on for idempotent provisioning). Every identifier-shaped input (username, workspace
name, role, password length, UUID text) is validated *before* any request is built, so a bad
caller input never reaches the wire. The caller's own API key is redacted out of every raised
error message and refused outright (before any header is built) if it contains a control
character (the same CRLF-header-injection defense the MLflow client uses for its bearer token).

**`tests/tasks/test_ftf_r006_p1_client.py`** (new, no-network, loopback HTTP stub scripted to the
verified real response shapes -- see the fault -> RED table below).

## Mutation-gate survivors -- disclosed, not force-closed (2 of 153)

`client.py:246` (`if _UNSAFE_KEY_CHARS.search(self._api_key):`) and `:253`
(`raise ArgillaRejectedError("API key contains control characters")`) -- the explicit
control-character check on the caller's own API key before building the auth header.

Verified empirically, not assumed equivalent by inspection alone: `packages/security/
outbound_guard.py`'s own `guarded_fetch` wraps its `conn.request(...)` call only with
`except OSError` (not `ValueError`), so a bare `ValueError` raised by `http.client`'s own
`putheader()` validation (CRLF in a header value) propagates up uncaught into this module's
`_call`, whose own generic `except ValueError:` fallback already raises the identical
`ArgillaRejectedError` class with an equally static, key-free message
(`"Argilla request could not be sent"`). Disabling the explicit check and re-running the
suite confirmed this directly: the same exception type is raised, and
`test_api_key_never_echoed_and_control_chars_refused`'s own `len(stub.seen)` assertion (no new
request logged) still held, because `HTTPConnection.request()` calls `putrequest()` (which
connects) before `putheader()` (which raises), so the stub never receives a parseable request
either way. The only real difference is one wasted TCP connect/putheader attempt. The FTF-R005
MLflow client this module mirrors has the structurally identical pattern (an explicit token
check plus a generic `except ValueError` fallback with its own static message) and would
likely show the same result under the same scrutiny -- not re-verified here, since editing that
already-certified module is outside this round's own write set.

Flagged here for a Control-plane `docs/certifications/mutation-allowlist.yaml` ruling
(`RELAY_FORBIDDEN_EXACT` -- relay has no write access to that file) rather than silently
allowlisted or contorted into an artificial test distinction.
