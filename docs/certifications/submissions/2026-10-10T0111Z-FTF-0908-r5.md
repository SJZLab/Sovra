## The return's finding

Round 4's own `FTF-0908-R4-1` real-Postgres check caught `ExternalProviderDeniedError` **outside**
the `with tenant_scoped_session(...)` block:

```python
try:
    with tenant_scoped_session(bare_factory, org1_id) as session:
        authorize_external_provider(...)
except ExternalProviderDeniedError:
    pass
```

`tenant_scoped_session` is `yield session; session.commit()` inside a `try`, with
`except BaseException: session.rollback(); raise` around the `yield`. Because nothing inside the
`with` body caught the exception, it always propagated through the generator's `yield`, so the
scope **always** took its rollback path — the check never exercised what happens on a *normal*
exit (the real calling pattern: a caller catches the denial to turn it into a 4xx, it doesn't let
it propagate).

That matters because of a specific, verified Postgres rule (PostgreSQL `SET` reference, every
version 10–18; confirmed via a web search this shift, see Sources below): a plain `SET` (i.e.
`set_config(.., is_local=false)`) issued inside a transaction that is later **rolled back** is
undone right along with the rest of that transaction — identically to `SET LOCAL`. The two
*only* differ on **commit**: `SET LOCAL`'s effect ends there; plain `SET`'s effect survives for
the rest of the session. So a buggy session-level re-bind (fault F2: "re-bind replaced by a
hand-written `set_config(..., false)`"; fault F2g: "a module-local `set_tenant_context` doing the
same, call text unchanged") is **invisible** to a check that only ever rolls back — rollback hides
the bug exactly as well as a correct transaction-local re-bind would. Only a check that lets the
scope **commit** can tell the two apart.

## The fix

1. `_rebind_leak_probe` (new helper) runs one denial per call, catching
   `ExternalProviderDeniedError` **inside** the `with` block, around only the
   `authorize_external_provider` call — the body then completes normally, so
   `tenant_scoped_session` takes its `session.commit()` path. It returns what a fresh checkout of
   the same `pool_size=1` connection sees afterwards.
2. **R5-1 (new, runs first):** monkeypatches this module's `set_tenant_context` name to a
   session-level `set_config(.., false)` — the observable shape of both F2 and F2g (a monkeypatch
   changes what the imported name resolves to without touching any call-site text, which is
   exactly F2g's own description; it produces the identical runtime SQL as F2's hand-edited call
   site) — and asserts the probe now shows the leak (`guc == org1`, `visible == 1`). If this isn't
   RED under the fault, the real check below proves nothing.
3. Disposes `bare_engine` right after the fault probe. **Found and fixed during this shift's own
   verification** (see "What I actually ran" below): the fault's session-level `SET` survives both
   `COMMIT` and the connection pool's default rollback-on-checkin (neither clears a session-level
   setting — that is the leak being proven), so without disposal it would silently contaminate the
   next probe's shared `pool_size=1` connection and produce a false failure unrelated to the real
   code. Disposing forces a genuinely fresh physical connection for what follows.
4. **R4-1 (fixed):** the same commit-path probe, with the real `set_tenant_context` restored, on a
   connection the fault never touched — asserts no leak.
5. Corrected `docs/spec-matrix.yaml`'s FTF-0908 note (round 4's claim that its check already
   proved this was wrong — the check *could not* have proven it, for the reason above) and the
   module-level comment above the probe in the test file. `evidence_hash` updated to this file's
   sha1.
