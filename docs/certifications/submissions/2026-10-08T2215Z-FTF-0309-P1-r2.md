## Finding 3, disclosed: why no `proving_symbol` was set
Investigated both ways to do this and rejected both:
- **A new `FTF-0309-P1` entry in `docs/spec-matrix.yaml`.** Tried it, then measured the effect: `scripts/status.py`'s
  own denominator moved from `134/302` to `134/303`. Every prior prerequisite child slice (FTF-0308-P1, FTF-0501-P1,
  FTF-0516-P1) has no entry of its own for exactly this reason (`docs/certifications/queue.md`'s own Backlog note:
  "these are refinements, not new criteria: the denominator stays 302"). Reverted.
- **Setting FTF-0307's own (`certification_state: CERTIFIED`) `proving_symbol` to `classify_training_capability`.**
  This route genuinely is a real caller, and the dominant codebase convention is exactly "blank until a live caller
  exists, then filled in" -- but measuring it exposed that `product_truth_check.py`'s `find_callers` *already*
  finds a caller for this symbol with or without this route: `evals/reference/candidate_discovery_from_org_litellm.py`
  (FTF-1706's own module) calls `classify_training_capability` directly. Unmounting this task's own router from
  `apps/api/app/main.py`, or even deleting this route's own call site entirely, left `product_truth_check.py`'s
  count unchanged (confirmed by direct fault injection, both ways, reverted after). Setting `proving_symbol` there
  would be a claim this task's own work does not actually drive -- no fault in *this* task's own diff reddens it,
  which is exactly the thing Law 1 asks every claim to survive. Reverted.

Recommend Control plane either: (a) decide FTF-0307's `proving_symbol` should be set anyway, crediting FTF-1706's
pre-existing caller (a decision about FTF-0307's own record, properly made by whoever reviews FTF-0307 or FTF-1706,
not unilaterally by this task's diff); or (b) drop this DoD bullet for FTF-0309-P1 specifically, since the
denominator-safe target doesn't exist and the only live caller for the one pure-logic symbol this route composes
already has a different, unrelated owner.
