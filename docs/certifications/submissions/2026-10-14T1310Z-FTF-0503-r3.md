## Return items

1. **WHOLE-DOCUMENT-BUFFERED** — fixed. Round 2 read the entire source into a `bytearray`, then `bytes`, then
   one decoded `str` before locating any element (`buf = bytearray(); for chunk in self._reader: buf.extend(chunk)`).
   Replaced with `_Cursor`: an incrementally UTF-8-decoded (`codecs.getincrementaldecoder`, chunk-boundary safe),
   prunable `str`-like view fed on demand from `ChunkReader`'s own chunks. `_skip_value`/`_scan_array`/`_scan_object`
   are unchanged in interface — they still take a plain `str` or the cursor interchangeably via `_peek`'s
   `IndexError`-based exhaustion check, so every existing direct unit test against a literal `str` still passes
   unmodified. `_generate` is the only caller that builds and drives a `_Cursor`, pruning it after each record.
   Pruning is batched (a 1 MiB staged-discardable threshold, `_Cursor._PRUNE_THRESHOLD`) rather than re-slicing the
   buffer on every record — a naive "prune immediately" re-slice is itself an O(len(buffer)) copy, which made an
   early version of this fix quadratic in practice (measured directly: a single-chunk 32 MiB document took minutes
   before batching was added). Proven: `test_memory_is_bounded_not_whole_document` (realistic 64 KiB chunking, the
   same convention `test_ftf_0502.py`'s own `test_memory_huge_record_is_discarded_not_buffered` uses; an 8 MiB
   document's peak stays under 2x a ~3 MiB document's own peak and under 1/2 the document's own size — bounded, not
   scaling with document size).

2. **EXPECTED-SHA-MISMATCH-COMPLETES** — fixed. A caller's `expected_sha256` is now compared against the
   `ChunkReader`'s own declared `_expected_sha256` before a byte is read — the identical fix `jsonl_importer`
   round 3 already applies for the same gap. Test `test_expected_sha_mismatch_is_source_changed_before_any_byte`
   (plus the positive control, `test_expected_sha_agreement_still_imports`).

3. **STRUCTURE-ERRORS-NOT-FATAL** — two real, independently reproduced scanner bugs, not merely a paraphrase of
   the finding:
   - `_skip_value`'s bracket branch tracked nesting *depth* only (`{`/`[` both +1, `}`/`]` both -1), so a
     mismatched pair like `[1, 2}` was silently accepted as one complete, well-formed value. Fixed with a stack of
     the actual opening characters; a closer that does not match the stack's own top raises `_Unterminated`.
     Reproduced directly against the pre-fix module (`ji._skip_value("[1, 2}", 0)` returned `6`, not an error) and
     pinned in `test_mismatched_bracket_types_are_fatal`.
   - A bare literal directly abutting a `"` with no separator (`1"]"`) was scanned straight through the quote as
     "more literal text" (the bare-literal scanner's terminator set did not include `"`), stopping only at
     whichever real terminator character came next — which, crafted adversarially, can be a bracket that belongs
     to an *embedded string's own content*. Round 2's own two independent passes over the same document (a
     whole-document `_skip_value` check in `_locate_container`, and the real per-element `_scan_array` that
     actually emitted records) then silently disagreed about where the array ends: **reproduced directly**,
     `run_json_import` on `[1, 1"]", 2]` returned `state == "completed"` with only 2 of the 3 real elements seen,
     no error at all. Round 3's single unified pass (`_scan_root` → `_stream_array` / `_stream_object_for_container`,
     no second re-scan of the same region to possibly disagree with the first) plus adding `"` to the bare-literal
     terminator set close this — a legitimate JSON literal (a number, `true`, `false`, `null`) never legitimately
     abuts a quote, so no valid document's outcome changes. Pinned in
     `test_adjacent_literal_and_string_is_fatal_not_dropped`.

   Structural failures now carry a real byte-offset `fatal_locator` (`object:<n>`, the position the scan was at)
   instead of round 2's fixed `object:0` placeholder for every document-level failure — pinned in
   `test_fatal_locator_is_a_real_byte_offset` and the "not object:0" assertion in the test above. Content-type,
   encoding and unmapped-top-level-key failures (no more precise single position to blame than the document
   itself) still use `object:0`, disclosed as a scope choice, not every code's locator was changed.

4. **OVERSIZE-ELEMENT-ENDS-IMPORT** — fixed. Removed the fatal `field_too_large` tier entirely (unlike CSV/XLSX,
   this scanner already knows an element's exact span via bracket/quote tracking *before* parsing it, so there is
   no cost reason to ever abort the whole document over one oversize element). Every size over
   `max_record_bytes` is now `RowRejection record_too_large` and the import continues — checked first by a cheap
   character-count lower bound (UTF-8 byte count is never less than character count, so a span whose character
   count alone already exceeds the limit is never sliced or encoded to confirm it). `JSON_FATAL_CODES` no longer
   declares `field_too_large`. Tests: rewrote `test_oversize_element_exact_boundaries` /
   `test_oversize_element_tiers` for the single tier, added
   `test_wildly_oversize_element_is_rejected_without_materialising_it` (a 50x-over-limit span, real neighbours
   still import).

## Mutation gate

`scripts/mutation_gate.py --base origin/main` (diff mode, exactly as CI's `mutation-gate` job runs it), full,
uncapped (`--max-mutants 0`): **199 run | 161 KILLED | 11 TIMEOUT | 27 SURVIVED | 0 allowlisted | score 86.4%.**
Local runs used a reduced test command (every `test_ftf_0503.py` check except the two `tracemalloc` memory tests,
which measure a wall-clock/memory property every mutant would otherwise re-pay the ~55s cost of) to keep
iteration practical; confirmed this reduced harness still detects real defects (a disabled content-type gate,
spot-checked) before relying on it, and the real CI `mutation-gate` job runs the full, unmodified file regardless
of what ran locally.

The 11 timeouts are infinite-loop mutants of `_Cursor`'s own exhaustion-check loops — the same accepted class
other importers' own mutation runs already document (e.g. FTF-0504 r3's "5 timeouts are infinite-loop mutants of
the parser and the prefix search").

Every one of the 27 survivors was individually reproduced by hand (the single mutant applied, the real test suite
run, the actual outcome read — not merely asserted) and falls into one of six genuinely equivalent classes, none
fixable by any behavioural test:

| class | lines | why it is equivalent |
|---|---|---|
| trivial property-getter return | `JsonImportOutcome.fatal_locator` (271) | identical reasoning to `jsonl_importer.JsonlImportOutcome`'s own already-confirmed case: the inserted "early return" is the literal same expression the real return statement evaluates |
| `_Cursor._grow` re-entry | 348, 355×2, 360, 361 | re-entering an already-finalized incremental decoder, or re-checking an already-true `done` flag, both empirically confirmed (direct interactive probing) to return the same value with no resident-data change — one harmless wasted call, not a behaviour change |
| exact tie-boundary comparisons | `__getitem__` slice growth (370), `prune` threshold (381) | the "off by one iteration" each mutant causes never changes the final returned substring or the final trimmed state, only how many harmless extra internal steps get there |
| single-already-isolated-character comparisons | 17 instances (`_skip_value` ×9, `_stream_array` ×2, `_stream_object_for_container` ×2, `_stream_container_value` ×2, `_scan_root` ×2) | the same equivalent class round 1's own `_max_nesting_depth` already established (a `.strip().lower()` of one already-isolated punctuation character can never differ from the character itself), extended here to every new scanner function |
| redundant cheap short-circuit | `_emit_record` line 604 | provably redundant with the exact byte-count check immediately below it (line 612, itself mutation-killed) — removing only the short-circuit never changes which records get rejected, only whether a possibly-huge span gets needlessly sliced first |
| chunk-merge-safe boundary | `_generate` head-byte count (810) | the incremental UTF-8 decoder is chunk-boundary-safe by construction, so merging one extra chunk into the BOM-sniffed head never changes the final decoded text |

**Two real test-coverage gaps found and fixed during this same pass** (not survivors in the final run, but real
defects reproduced in the first uncapped attempt, 75.9%): `_iter_object_members`'s colon-check (`_scan_object`'s
own generic helper) and three of `_stream_object_for_container`'s own raises were *masked* — a mutant removing
only that one check still let the same crafted input hit a different, un-mutated check reporting the identical
generic `json_malformed` code, so a test asserting only `(state, failure_code)` could not tell the two apart (the
exact class of issue `_scan_object`'s own colon check already had). Fixed by asserting the exact `fatal_locator`
byte offset (not just the failure code) in `test_nested_container_structural_fault_table`, and, for two of those
cases, by moving the fault to the *first* member of the document — `_stream_object_for_container`'s own
`key`/`key_end` locals are reused across loop iterations, so a removed raise after a later member's own key/value
parse failure does not crash (it silently falls through to a stale, still-bound value from an earlier,
successfully-parsed member) but a removed raise on the very first iteration genuinely has nothing to fall back on
and surfaces as an `UnboundLocalError`, which `main()`'s own exception wrapper correctly reports as a failure.
