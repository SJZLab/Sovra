## Finding 1 — CONFIRM-FOCUS-LOST (FIXED, with a real fault→RED→GREEN cycle)

The abandon-confirmation was a plain `<div role="alertdialog">` with no focus management at all:
clicking "Abandon this draft…" hid the trigger and showed the div, but focus stayed wherever it
was (on the now-detached trigger, i.e. nowhere); Escape did nothing; `aria-label="Confirm abandon"`
was a static string, not tied to the real consequence text.

Replaced with a new shared `apps/web/components/ui/Dialog.tsx` built on `@radix-ui/react-dialog`
(see "Dependency" below) — a real focus trap while open, Escape-to-close (treated as "Keep draft",
never as "Abandon"), `aria-labelledby`/`aria-describedby` wired to the real title/consequence text,
and `role="alertdialog"` preserved (UNPINNED finding 4).

**Focus RETURN surfaced a second, real bug while building this**, caught only by the real-Chromium
harness (see "Evidence" below) — jsdom's own `document.activeElement` bookkeeping did not reproduce
either version:

1. First attempt: the trigger button was conditionally unmounted (`{!confirmingAbandon && <Button>}`)
   in the same render that opened the dialog. Radix's `FocusScope` captures "previously focused
   element" at Content-mount time, by which point the trigger was already detached from the DOM —
   restore target fell back to `<body>`.
2. Second attempt: kept the trigger mounted but set `disabled={confirmingAbandon}` on it. Disabling
   a *focused* control blurs it synchronously (a browser behaviour, not React's) before any capture
   could run — same `<body>` result.
3. **Fix**: the trigger stays mounted, never disabled (the modal overlay already blocks interacting
   with it). Its `onClick` captures `event.currentTarget` into a ref (`abandonTriggerRef`), passed to
   the new `Dialog` as `restoreFocusTo`; `Dialog`'s `onCloseAutoFocus` calls `.focus()` on it
   directly instead of relying on Radix's default (which only works out of the box for its own
   `Dialog.Trigger`, not an externally-opened dialog).

## Finding 5 — CONFIRM-PROMISES-DISCARD (FIXED by rewording; no abort route exists)

Checked `apps/api/app/datasets/direct_object_storage_upload_routes.py`: it exposes
create/read-one/read-parts/part-urls/finalize only — no route the browser could call to abort an
in-progress upload session. `upload_sweeper.py`'s own docstring confirms abandoned sessions are only
reclaimed by a periodic sweep, "at most 24 hours" later, and that sweeper itself is `UNWIRED` in any
deployment yet. Control plane's stated preference was "abort the real route if one exists, otherwise
reword" — no route exists, so reworded.

Old: *"Abandon this draft? The partly uploaded file is discarded and a new upload starts from the
beginning. This cannot be undone."* — this claims the server-side upload is discarded, which nothing
in this confirm's own code path makes true.

New (`abandonConfirmBody` in `apps/web/components/ui/phrases.ts`, en/ar): *"This browser forgets your
progress and a new upload starts from the beginning. This cannot be undone."* — describes only what
confirming actually, honestly does. Test: `FTF-UX02 r2 finding 5: the confirmation no longer claims
the upload itself is discarded`, asserting the body does not match `/discarded/i` and that confirming
makes zero `fetch` calls (already covered by the existing `fetchCalls().length).toBe(0)` assertions).
