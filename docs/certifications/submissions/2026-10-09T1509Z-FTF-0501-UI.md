## What shipped
- `apps/web/components/dataset-factory/resumable_dataset_upload_ui.tsx`: a real file-picker
  component consuming only the five frozen FTF-0501 routes (`build_direct_upload_router`): create
  session, read, list parts, request part URLs, finalize.
  - Purpose and declared content type are an explicit choice from the server's own closed
    vocabularies (`ALLOWED_PURPOSES`, `SUPPORTED_CONTENT_TYPES`, redeclared from
    `dataset_source_connection_schema.py`/`direct_object_storage_upload.py`), never inferred from
    the file name.
  - The declared SHA-256 and size sent on create are the real `crypto.subtle.digest("SHA-256", ...)`
    of the picked file's bytes (via `FileReader`, portable to jsdom and every browser), not a
    placeholder.
  - Per-part progress and upload are driven by the session's own real `part_size_bytes`/
    `part_count`/`declared_size_bytes` (`partByteRange`); this file never re-derives the server's
    part-size default.
  - Resume (both a mid-upload network drop and a page reload) always re-lists parts first
    (`GET .../parts`, the real source of truth) and computes `missingPartNumbers` from that listing
    before requesting any URL — never a blanket re-upload of every part.
  - A reload restores from a small, non-sensitive `localStorage` draft (session id + declared
    fields + file name only — Section 72.2's own "Wizard stores actual selected IDs ... and
    progress"). Resuming from that draft requires re-picking the file and recomputing its SHA-256;
    a mismatch (wrong file) is refused before any network call.
  - The six typed finalize outcomes (201 accepted, 409 `upload_incomplete`, 409 other/410 expired/422
    rejection reasons, 503 storage outage) are each a distinct, visible state (Law 17). A 503 or a
    409 `upload_incomplete` keeps the draft (the session stays open server-side); every other
    terminal outcome clears it.
  - Presigned part URLs are used only in memory inside the upload loop and are never written to
    `localStorage`, including under the additive leak fault tested below.
- `apps/web/tests/ftf_0501_ui.spec.ts`: a real DOM-level Vitest + React Testing Library spec against
  this actual component (mocked `fetch`; real `File`/`Blob` slicing via `FileReader`, real
  `crypto.subtle` hashing — not mocked). 20 tests.

## Fault → RED (run as CI does: `pnpm exec vitest run apps/web/tests/ftf_0501_ui.spec.ts`)
Each mutant was applied to the real production component, shown RED, then reverted byte-identical
(confirmed via `cp` from an untouched backup, not by trusting the diff).

| # | Fault (in `resumable_dataset_upload_ui.tsx`) | Result |
|---|---|---|
| F1 | Resume ignores the real `GET .../parts` listing and re-requests every part number (the literal "resume re-uploads every part" fault this item's own DoD names) | RED — 2 tests (drop-then-resume, reload-then-resume) |
| F2 | `finalize()` treats every HTTP status as accepted (the literal "409 shown as success" fault this item's own DoD names, generalized to every non-201 status) | RED — 7 tests (incomplete, expired, size/sha256/content-type mismatch, version conflict, storage outage) |
| F3 | Additive leak: after receiving part-URL grants, write the first grant's presigned URL into a second `localStorage` key "for debugging" | RED — 1 test (secret-never-persisted, which scans every key this origin's `localStorage` holds, not only the draft key) |
| F4 | Remove the resume file-identity check (`if (false)` in place of the SHA-256/size comparison) | RED — 1 test (mismatched file must be refused before any network call; with the check removed the component instead proceeds and the mocked `GET` session call is unexpected, so `fetchCalls().length` is no longer 0 and the resume banner is replaced by a network-error state) |

Negative tests that run the real default code with the real inputs they describe: a file named
`looks-like-a.csv` sent with the content-type select left at its default still declares
`application/json` (never inferred from the name); a resumed file whose bytes differ from the
draft's declared SHA-256/size is refused before `fetch` is called at all; a dropped PUT mid-upload
(a thrown `fetch`) is shown as `interrupted`, never as progress or success; the create/finalize/
part-URL request bodies are asserted field-for-field, not just "a POST happened."

No host-config dependence (no git/env/locale reads; `crypto.subtle` and `FileReader` are both
plain Web APIs available under jsdom as exercised here and in every real browser), so no
neutral-host rerun applies.
