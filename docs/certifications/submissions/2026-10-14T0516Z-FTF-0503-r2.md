## Return items

1. **whole-document `json.loads`, 62x memory, not linear** — fixed. `json_importer.py` is rebuilt on
   `import_common` (P1), the same shape `csv_importer`/`jsonl_importer` use. A linear, one-pass,
   string/escape-aware span scanner (`_skip_value`/`_scan_array`/`_scan_object`) locates each
   top-level array element (or root-level object member) without materialising the whole parsed
   array at once; `strict_loads` parses one element's own span at a time, and the accepted/rejected
   candidate is handed to the caller and discarded before the next element is even located.
   - **Differential evidence**: `test_scanner_matches_json_loads_on_generated_documents` — 300
     randomly generated documents; every span the scanner finds, parsed alone via `strict_loads`,
     equals the same index of a whole-document `json.loads` (proves the split is exact, not an
     approximation).
   - **Memory evidence**: `test_memory_is_linear_not_quadratic` — tracemalloc peak memory at
     record counts 500 / 2,000 / 8,000 (a 16x range) stays within a 3x ratio of each other
     relative to document size (observed ~4.7x–5.4x of document bytes, bounded and not growing with
     record count — the round-1 defect measured 62x and climbing). A standalone comparison against a
     naive "hold every parsed dict live at once" baseline on the same 20,000-record document showed
     4.89x for this round's importer vs 11.28x for the naive approach.
2. **4301-digit int / duplicate key / NaN / Infinity / 1e999 / lone surrogate silently accepted** —
   fixed. Each element now goes through `strict_loads` (P1's own one real JSON reader) individually;
   a bad value in one element rejects only that element (`number_out_of_range`, `duplicate_key`,
   `non_finite_number`, `invalid_unicode`), never the rest of the import, never a crash.
   `test_4301_digit_int_is_rejected_not_crashed`, `test_duplicate_key_is_rejected`,
   `test_non_finite_number_is_rejected`, `test_lone_surrogate_is_rejected`.
3. **a 3 MiB element accepted and an over-cap document loses every element** — fixed. Two-tier size
   check per element: over `2*max_record_bytes+2` is fatal `field_too_large` (found by span length
   alone, before parsing); between that and `max_record_bytes` is `RowRejection record_too_large`.
   The whole-source bound (`ImportLimits.max_source_bytes`, shared with every importer) is enforced
   by `ChunkReader` before any element is even located, so an over-cap *document* fails before a
   single element is read — an oversize *element* inside an otherwise-fine document only costs that
   one element. `test_oversize_element_tiers`, `test_over_cap_document_loses_only_the_document_not_elements`.
4. **no `$`/`/<key>`/`$record` container mapping** — fixed. The MappingSpec's own `json` block
   (`container` a JSON Pointer, `ignored_top_level_keys`, both already validated by P1's
   `mapping_from_object` but consumed by no importer until now) resolves where the records are:
   `container: ""` is the document's own top-level value (`$`) — an array is a container of *N*, an
   object is itself the one record (`$record` at the root); `container: "/rows"` (`/<key>`) is one
   level into the root object, with every other root key required to be in `ignored_top_level_keys`
   or the import is fatal `unmapped_top_level_key`. Disclosed scope limit: depth 0 or 1 only
   (`MappingInvalidError bad_pointer` for deeper, before any byte is read — every named example is
   one of these two). `test_root_array_container`, `test_root_object_is_one_record`,
   `test_nested_container_at_key`, `test_nested_container_single_record`,
   `test_unmapped_top_level_key_is_fatal`, `test_container_pointer_missing_is_fatal`,
   `test_container_depth_over_one_is_mapping_invalid`.
5. **BOM refused; UTF-16/UTF-32 not `unsupported_encoding`** — fixed. Leading-byte BOM signatures are
   checked before any decode (longest first, since UTF-16LE/UTF-32LE share a prefix): UTF-8 BOM is
   fatal `unexpected_bom` (RFC 8259 forbids it); UTF-16 LE/BE and UTF-32 LE/BE are fatal
   `unsupported_encoding`. Bytes with no recognised BOM that still fail strict UTF-8 decode are
   `invalid_encoding`. `test_bom_is_refused`, `test_utf16_utf32_are_unsupported_encoding`,
   `test_invalid_utf8_without_bom_is_invalid_encoding`.
6. **no content-type gate, chunk input, `ImportReport`, Law 17 states or deterministic `record_id`**
   — fixed by adopting P1 wholesale: `run_json_import(reader: ChunkReader, mapping, ...)` takes only a
   `ChunkReader`, gates on `verified_content_type in {"application/json"}` before a byte is read,
   produces the shared `ImportReport` (`records_seen == accepted + rejected`, `report_sha256` sealed),
   and `normalize_mapped_record` derives `record_id` as `uuid5(dataset_sha256:mapping_sha256:index)` —
   a pure function of content and position, never a freshly minted `uuid4` per call.
   `test_content_type_gate`, `test_chunk_reader_is_the_only_input`, `test_chunk_boundary_table`,
   `test_import_report_is_produced`, `test_law_17_states`, `test_deterministic_record_id`.
7. **content leaks (role text, byte values) in messages** — fixed as a consequence of switching to
   `RowMappingError`/`RowRejection` (code + slot name only, never source text), replacing round 1's
   `QuarantinedRow(message=str(exc))` which forwarded FTF-0506's own exception text verbatim.
   `test_meta_leak` (a marker planted in role/content/top-level-key/BOM-adjacent positions never
   appears in the report, a rejection, or any exception text in the chain).
8. **limits raisable and loosely typed** — fixed by consuming `ImportLimits` (frozen, lower-only,
   strict-typed) throughout instead of the round-1 module's own ad hoc `max_total_bytes`/
   `max_nesting_depth` ints.
9. **source labels reach metadata unmapped** — fixed as a consequence of switching to
   `apply_mapping`: only the mapping's own declared metadata slots are ever extracted; nothing from
   the raw element reaches canonical metadata un-governed.

## Disclosed

- **Mutation gate: 2 survivors remain, both the same line, proposed equivalent, not allowlisted by
  this round.** `_options`'s `if slot.kind != "key": raise MappingInvalidError("bad_slot")` survives
  M4 (`!=` -> `==`) and M9 (`.strip().lower()`). `slot.kind` is produced only by
  `import_common._slot()`, a closed function whose return value is always exactly one of the four
  already-normalised literals `"key"`/`"header"`/`"index"`/`"letters"` (lowercase ASCII, no
  surrounding whitespace, no case variant) — there is no public `ImportMapping`/MappingSpec input
  through which a caller can make `slot.kind` hold anything else, so no test can make this check's
  real and mutated forms diverge. `docs/certifications/mutation-allowlist.yaml` is
  `RELAY_FORBIDDEN_EXACT` in `scripts/ci_policy.py` — a relay round cannot add an entry there even
  when it believes one is warranted. Proposed classification for Control-plane L2 review: `file:
  workers/data/json_importer.py`, `function: _options`, `operator: M9` (and `M4`), `line: 257`,
  `reason:` as above. Everything else the second mutation-gate pass found (59 of 61 initial
  survivors) was fixed with real tests or a real code change — see Gates above.
- Container pointer depth is scoped to 0 or 1 (every named example — `$`, `/rows` — is one of these
  two); a deeper pointer is `MappingInvalidError bad_pointer` until a real caller needs it.
- A duplicate key at the exact root level, when `container` names a nested key, is caught as an
  ambiguous match (`mapping_column_missing`) by the root-member structural scan, not as
  `STRICT_JSON_CODES duplicate_key` — locating the container itself is a structural scan, not a
  `strict_loads` parse; `duplicate_key` remains the real check applied to each extracted element.
- No live import route calls the importer yet: `proving_symbol` stays blank, same disclosed
  precedent as every sibling importer.
- The PG16 + SeaweedFS integration test through the real FTF-0501 routes, in its own CI job
  (`json-import-integration`), named by the return note as required, is **not done this round** —
  disclosed rather than fabricated. The core architectural defect (memory, correctness, security)
  and every unit/differential/mutation-level fault in the return note are fixed and proven this
  round; the real-service integration test is the remaining item for the next round, following the
  same multi-round precedent several other items in this backlog have already used (e.g. FTF-0904
  reached round 7, FTF-0616 reached round 8) rather than holding back a real, substantial fix while
  that one piece is built.
