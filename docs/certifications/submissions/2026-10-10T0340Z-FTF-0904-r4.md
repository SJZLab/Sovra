## E (reproduce first, then fix)

### `_PREFIXES`'s JWT alternative

First hypothesis (wrong, disclosed so the next session doesn't repeat it): `"eyJ" * k` should be
quadratic the same way the round-3 percent-token shape was. Measured directly against the real
compiled `_PREFIXES` — **linear** (0.018 µs/char flat from 100 KB to 1.6 MB). Root cause: the
rule's own leading `(?<![A-Za-z0-9])` lookbehind rejects every repeat after the first, because
each repeat of literal `"eyJ"` is preceded by `"J"`, a letter. The bare construction was hiding
the real defect, not exercising it.

Second construction: `_` satisfies the lookbehind (not `[A-Za-z0-9]`) **and** is itself a member
of the segment's own class (`[A-Za-z0-9_\-]`), so it does not stop the greedy consume either —
every `"_eyJ"` repeat is a genuine, independent trigger, each re-scanning the rest of the text for
a `.` that never appears. Measured against the real, unmodified `_PREFIXES` (git-stashed back to
confirm it's the on-disk pre-fix code, not a reconstruction):

| size (chars) | time |
|---|---|
| 10,000 | 0.087s |
| 20,000 | 0.347s |
| 40,000 | 1.47s |
| 80,000 | 5.78s |
| 160,000 | 23.16s (confirmed again directly against the stashed original: times out at 15s) |

us/char roughly doubles with each doubling of n (quadratic, not linear).

Third step (also disclosed as a dead end): converting the segment to possessive alone
(`{5,}+`, no upper bound) did **not** fix it — `"_eyJ" * 40,000` (160 KB) still took 23s. Why:
possessive removes the wasted *backtrack* after a failed greedy consume, but the wasted work
here is the repeated O(remaining) **consume** itself, happening independently at every one of
O(n) "eyJ" repeats; possessive doesn't touch that. Confirmed the fix needs a bound on the
quantifier's own maximum, not just possessive: `{5,4096}+` is linear but with a large constant
(1.13s at 160 KB, extrapolating to ~1.8s at 256 KB — too close to the 4s cap for comfort);
`{5,1024}+` is linear with a comfortable margin:

| size (chars) | `{5,1024}+` time |
|---|---|
| 160,000 | 0.29s |
| 320,000 | 0.56s |
| 640,000 | 1.13s |
| 1,280,000 | 2.29s |
| 2,560,000 | 4.61s |

Doubling n roughly doubles time at every step (linear). A real JWT (`eyJhbGciOiJIUzI1NiJ9.
eyJzdWIiOiJ1c2VyLTEifQ.sig`) is still redacted correctly after the bound (checked directly).

### `_QUOTED_VALUE`

Spent considerable effort trying to reproduce a genuine multi-trigger quadratic blowup for the
bare-quote alternatives (`"[^"\r\n]*"`, `'[^'\r\n]*'`) and the escaped-quote one
(`\\+"[^"\r\n]*?\\+"`), using the same "lookbehind-defeating separator" technique that found the
real JWT defect, plus every construction already in `_ADVERSARIAL` (`quote-run`,
`backslash-quote`). All of them measured **linear**, including with the `_` and space separator
tricks. Reasoned why, and it holds up: for all three alternatives, the trigger character that
*opens* a value is the same character the alternative's own class *excludes* (a bare quote for
alt2/alt3; a backslash-prefixed quote for alt1). That means every repeat of the trigger is itself
a stopping point for the repeat before it — the construction is **self-bounding**, unlike the JWT
case where `"eyJ"` (the trigger) and `"."` (the required literal) are unrelated characters, so a
`.`-free run of `eyJ`-repeats never introduces a stopping point at all.

Given that, the bare-quote alternatives need no bound — possessive alone is correct and
sufficient (confirmed: `*+` does not change which matches succeed here, because the one possible
split point is already fixed by class exclusion; backtracking could never find a different one,
only waste time trying). The escaped-quote alternative's middle allows backslashes (unlike the
bare ones), so it is not purely self-excluding in the same way and cannot be made possessive
without risking a different match on real nested-JSON-escaped input; it is bounded instead, to
8192 characters, which closes the one case the self-bounding property doesn't cover on its own
(a single, very long, genuinely unterminated escape run) without changing any existing test's
result.

### Fix

- `_PREFIXES`: JWT alternative segments bounded and possessive: `{5,}` → `{5,1024}+` (both
  middle segments), `*` → `*+` (trailing segment, no bound needed — nothing follows it, so
  there's no backtrack-on-missing-literal cost to remove; possessive only for consistency).
- `_QUOTED_VALUE`: bare-quote alternatives possessive (`*` → `*+`), escaped-quote alternative's
  middle bounded (`*?` → `{0,8192}?`).
- Docstring (module-level and at `_QUOTED_VALUE`'s own definition) updated to disclose both
  bounds and explain why possessive alone was/wasn't enough in each case.
