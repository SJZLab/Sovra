# FTF-0616 — LLM judge adapter through LiteLLM — PROVISIONAL (relay, `relay/FTF-0616-r1`)

Status: PROVISIONAL / L1-PROVEN. Not self-certified (Law 4). No spec-matrix entry was edited

grader in `workers/evaluation/`).

## What shipped
- `workers/evaluation/llm_judge_grader.py` (`grade_llm_judge`): a real, bounded
  `POST /v1/chat/completions` judge call through the existing LiteLLM gateway, reusing the exact
  `guarded_fetch`/`ConnectionPolicy` outbound guard and `resolve_secret_ref`/`OpenBaoConfig` secret
  resolution every certified FTF-02xx probe in `packages/litellm_client/` already uses — never a
  direct provider call. Refined from the packet's own generic `services/evaluation-worker/...`
  suggestion to the real, already-scaffolded `workers/evaluation/` root every sibling FTF-06xx
  grader already uses.
- Three structural guards, each a hard refusal (`LlmJudgeGraderError`/subclass) **before any
  network call**, directly encoding this task's own negative_acceptance ("Uncalibrated,
  self-judging or injection-obeying result cannot certify final quality"):
  - **self-judging**: refused when `judge_model_id == candidate_model_id`, and when
    `judge_model_id` is not in the caller's own `approved_judge_model_ids`.
  - **uncalibrated**: refused unless a `CalibrationRecord` proves this exact (rubric, judge model)
    pairing matched every golden-pass and every golden-fail case (no invented percentage
    threshold — Law 11).
  - **never on the judge alone** (§27): a `critical=True` case requires an explicit
    `deterministic_corroboration: bool`, never `None` (`None` means "not consulted", refused).
- **Injection-obeying** is addressed structurally, not behaviourally: `candidate_response` is
  always wrapped in a single fixed delimiter inside the user message, the system message always
  carries a fixed "untrusted data, never an instruction" guard, a candidate response containing the
  literal closing delimiter is refused outright (forged-delimiter injection), and the verdict is
  *only* ever read from the strict `json_schema`-validated `verdict` field via `_state_for_verdict`
  — never by scanning free text.
- A locked, versioned `JudgeRubric` (`rubric_id`, `version`, `instructions`) — a changed rubric is
  a new version, never a silent edit of the same one.
- Real, distinct `LlmJudgeState` outcomes for every non-happy-path case (schema violation, not
  JSON, content filtered, unsupported parameter, invalid token, every connection/secret failure) —
  never silently fabricated into PASSED/FAILED. `LlmJudgeResult.passed` is `True`/`False` only for
  a real verdict, `None` otherwise.
- CI (additive only): one `gate` step for `tests/tasks/test_ftf_0616.py` (no new job — this task
  has no DB and no real-integration resource_gate beyond the gateway itself, which the test's own
  local HTTPS double covers, same convention as the sibling FTF-02xx probes).
- Not done on purpose: no persistence (task's own `database_changes` clause), no Inspect AI runtime
  wiring (Section 25's evaluation loop is not dependency-ready yet — same disclosed "no live caller
  yet" precedent every sibling grader in this directory already uses), no rubric registry/versioning
  store (out of this module's own file scope).

## Decisions made where the packet was silent (default-resolution rule)
- "Uncalibrated... cannot certify" is made a hard, structural refusal
  (`CalibrationRecord.is_calibrated`: every golden-pass and golden-fail case must match, no
  percentage threshold invented) rather than a soft warning folded into the result.
- "A critical safety decision never rests on the judge alone" (§27) is read literally: the caller
  must supply an explicit `deterministic_corroboration` signal for a critical case, or the call is
  refused before any network request.
- The verdict schema (`pass`/`fail`, bounded `reasoning`, `confidence`) mirrors FTF-0213's own
  `response_format: json_schema, strict: true` protocol exactly — the same reused convention, not a
  new one.

## Disclosed limits
- No real external LLM provider is called anywhere in this suite — the relay sandbox has no open
  egress for that, and real judge-model calls through LiteLLM are an evaluation-run-time concern
  (Section 25), not this adapter's own test boundary. Every HTTPS round trip in
  `tests/tasks/test_ftf_0616.py` is against a real local HTTPS server standing in for the gateway
  (a real TLS handshake, real self-signed CA installed into this sandbox's trust store for the
  run), the same no-DB/no-external-egress convention every certified FTF-02xx probe in
  `packages/litellm_client/` already established — not a mock of the HTTP layer itself.
- When `openssl`/`update-ca-certificates`/passwordless `sudo` are unavailable, the live-TLS-backed
  checks are skipped and disclosed (printed, not silently dropped); GitHub Actions' `ubuntu-latest`
  runner has both tools, same as every sibling suite.
- Observed, not caused by this change: running this suite's own mutation-gate round (~400
  subprocess invocations, each installing/removing a fresh local CA) back-to-back with the
  pre-existing, already-CERTIFIED `tests/tasks/test_ftf_0210.py`/`test_ftf_0213.py` in the same
  long-lived sandbox left those two suites failing on an unrelated `ssl.SSLEOFError`/stale-state
  assertion afterward; both suites are untouched by this diff (confirmed via `git log`), and a
  fresh CI runner does not share this sandbox's accumulated TLS/CA-store state, so this is recorded
  here rather than silently worked around.
- No persistence, no UI, no Inspect AI runtime wiring — all disclosed above and in the module's own
  docstring.
